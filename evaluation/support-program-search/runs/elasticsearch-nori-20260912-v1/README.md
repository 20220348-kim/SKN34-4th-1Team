# Elasticsearch + Nori 첫 후보 검색 비교

## 실행 전에 고정한 계획

- 입력: `../support-program-catalog-20260906-v1/review-final-v1/fixture-labeled.json`.
  기준일 2026-09-06, 공고 1,422건, 질문 16개, 기존 AI-only 라벨과 split 유지.
- 비교: 기존 exact-token-count 키워드 / standard BM25 / Nori(`mixed`) BM25.
  모든 방식 K=20. ES 설정은 `../../elasticsearch/index.json`에 고정.
- 본문 전체에 같은 가중치를 사용하고 동의어·지역 예외·질문별 튜닝은 하지 않는다.
- 16개 질의 첫 패스 + 반복 3회. dev·heldout을 함께 기록하되 이를 보고 설정을 바꾼 재실행을
  최초 미사용 검증처럼 표현하지 않는다.
- OpenAI·임베딩·Qdrant 호출 0회. 기존 서비스와 데이터는 변경하지 않는다.
- 새 후보 판정은 이번 범위가 아니다. AI-only pooled-reference Recall만 진단용으로 계산한다.
  양성 2개로 전체 검색 품질을 입증하지 않으며, 라벨·실행 조건을 결과에 맞춰 바꾸지 않는다.

실행 절차와 한계는 [실험 안내](../../elasticsearch/README.md)를 따른다.

## 실제 실행 결과 — 2026-09-12

**비교 도구와 실제 Nori 색인·검색은 동작한다. 그러나 이번 자료에서는 Recall 개선이 확인되지 않았다.**
운영 검색에 Elasticsearch를 연결하거나 기존 키워드 후보를 교체하지 않았다.
실제 엔진·검색 결과·설정·소스 해시·HTTP 시간·분석 토큰은 [report.json](report.json)에 보존했다.

| 방식 | 전체 후보 Recall@20 | dev(양성 1개) | heldout(양성 1개) | 반복 HTTP 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 기존 키워드 | 0.75 | 0.50 | 1.00 | 비교하지 않음 |
| standard BM25 | 0.75 | 0.50 | 1.00 | 13.73ms |
| Nori BM25 | 0.75 | 0.50 | 1.00 | 15.15ms |

- 16개 질문을 모두 검색했다. AI-only 참조 기준 평가 가능 6개, 그중 양성 2개, 제외 10개는 그대로다.
  위 숫자는 질문별 Recall의 평균이며 전체 정확도 75%라는 뜻이 아니다.
- Q02에서는 세 방식 모두 관련 공고 2개 중 1개만 찾았다.
  `BIZINFO:PBLN_000000000125904` 누락은 해결되지 않았다. Q14는 세 방식 모두 관련 공고 1개를 찾았다.
- 참조 풀에서 무관으로 분류된 4개 질문에는 세 방식 모두 후보가 생겼다(4/4).
  이번에는 AI 최종 필터를 실행하지 않았으므로 사용자에게 4건 오추천했다는 뜻이 아니다.
- HTTP 시간은 로컬 Docker, 샤드 1개, JVM heap 512MiB, 고정 공고 1,422건에서
  질의당 3회씩 총 48개 반복 표본을 측정한 것이다. standard 8.71~26.22ms,
  Nori 10.76~34.76ms다. 첫 패스 16개는 각각 11.81~79.78ms, 16.87~128.48ms로 따로 기록했다.
  ES 쿼리 캐시 전체를 제거한 실험이나 동시 부하 테스트가 아니며, 운영 채팅 속도와 비교할 수 없다.

### 실제 한국어 분석 예시

`_analyze`로 확인한 토큰이며 예상 결과를 작성한 것이 아니다.

| 입력 | standard | Nori |
| --- | --- | --- |
| 서울에서 창업지원을 받고 싶어요 | 서울에서 / 창업지원을 / 받고 / 싶어요 | 서울 / 창업 / 지원 / 받 / 싶 |
| 중소기업의 사업화 지원 | 중소기업의 / 사업화 / 지원 | 중소기업 / 중소 / 기업 / 사업 / 지원 |
| AI 인공지능 | ai / 인공지능 | ai / 인공지능 / 인공 / 지능 |

조사·복합어 처리는 확인되지만 `사업화 → 사업`처럼 구분이 줄어드는 경우도 있다.
AI와 인공지능이 동의어로 연결된 결과도 아니다. 한국어 토큰 분해 자체가 관련도·신청 자격 개선을 보장하지 않는다.

## 검증과 한계

- 전용 통합 테스트에서 `서울 창업 지원사업` 문서를 `서울에서 창업지원을`로 찾는 사례를 실제 ES로 확인했다.
  이는 AI가 작성한 합성 계약 테스트이지 실데이터 품질 점수가 아니다.
- 첫 기동 시 Docker Desktop internal-only 네트워크에서 호스트 포트 연결이 실패했다.
  공개 공고 색인 전 전용 bridge로 수정한 뒤 재검증했다. 운영 서비스·데이터는 변경하지 않았다.
- 고정 라벨의 출처 검증, 본문·전체 카탈로그 해시 검증, 반복 질의의 후보 순서 일치와 보고서 지표 재계산을 수행했다.
- 새 후보를 다시 판정하지 않았으므로 미판정 관련 공고가 있는지는 알 수 없다. 현재 자료는 Nori 도입의
  효과를 확정하기에 부족하다. 기존 3단계·4단계 보고서나 정답 라벨을 덮어쓰지 않았다.
- OpenAI·임베딩·Qdrant 호출은 0회다. 최종 추천 MRR과 운영 하이브리드 품질·지연은 미측정이다.

최종 검증 결과:

- 후보 평가 도구: 121건 실행, 120건 통과. 기본 실행에서 opt-in ES 통합 1건은 건너뛰었다.
- 실제 ES 환경의 새 테스트 파일: **13/13 통과, 건너뛰기 없음**. 위에서 건너뛴 통합 사례도 포함한다.
- 검토 도구 전체: **108/108 통과**.
- 기존 공유 판정·캡처 `verify-shared-run.py --with-capture`: 통과. 이번 실행은 저장 파일 검증만 했다.
- 새 비교 보고서의 API 없는 재계산, 실행 소스 SHA-256 대조, Compose 설정·이미지 빌드,
  workflow YAML 구문, 문서 링크, `git diff --check`: 통과.
- Core·AI·Frontend production 코드와 메인 Compose는 바꾸지 않아 애플리케이션 전체 테스트는 다시 실행하지 않았다.
  전용 GitHub Actions는 로컬에서 동등한 명령을 검증했으며 원격 workflow 실행은 하지 않았다.
- 종료 시 전용 실험 컨테이너·네트워크와 tmpfs의 복사 색인만 정리했다. 보고서·입력 스냅샷·실행 코드는 남아
  다시 색인할 수 있다. 기존 개발 컨테이너 6개는 실행 상태를 유지했다.

## 다음 판단

운영 전환은 보류한다. 한국어 표현 차이를 포함한 충분한 양성 질문·라벨을 별도 버전으로 준비하고,
동일한 의미 후보를 고정한 Qdrant+기존 키워드 대 Qdrant+Nori의 RRF 비교로 효과를 확인해야 한다.
기존 캡처의 **이미 결합된 후보**를 순수 Qdrant 결과로 취급해 다시 결합하면 안 된다.
현재 결과만으로 Elasticsearch가 불필요하다고 확정할 수도, 반드시 더 낫다고 확정할 수도 없다.
