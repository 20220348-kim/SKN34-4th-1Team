# 4단계 1차 개선 — 제한시간 정렬과 후보 검색 결합

## 측정 전에 고정한 범위

- 기준 코드: `2a5b205` (3단계 완료 후 merge).
- 비교 기준: `../actual-capture-v3/capture.json` 및 `../review-final-v1/fixture-labeled.json`.
- 동일한 `../fixture-unlabeled.json`, `../query-set.json`, 기준일 `2026-09-06`을 사용한다.
- 스냅샷 1,422건·질문 16개·dev/heldout·기존 AI-only 라벨·제외 질문을 변경하지 않는다.
- 모델 `gpt-5.6-luna`, 임베딩 `text-embedding-3-small` 1,536차원, 기존 랭킹 프롬프트·점수 정책을 유지한다.
- 의미 검색 top 20과 기존 평가 기준과 같은 본문 토큰 일치 top 20을 동일 가중치 RRF로 결합한다.
  `sum(1 / (60 + 1부터 시작하는 순위))`, 동점이면 의미 검색 순위·제공처 포함 ID 순이다.
  키워드 점수 동점은 최신순·제공처 포함 ID 순이다. 최종 후보는 여전히 20개다.
- RRF 상수·검색 깊이는 이 실행에서 튜닝하지 않는다. 지역·업종·정답 ID별 규칙은 추가하지 않는다.
- 의미 검색 장애를 키워드 결과로 숨기지 않는다. DB·색인은 변경하지 않고 읽기 전용으로 실행한다.
- 제한시간 기본값은 모델 25초 / Agent 30초 / Core 35초 / 화면 70초로 정렬한다.
  기존 캡처의 평가용 25/30/35초와 동일하므로 모델의 대기 조건도 비교 가능하다.
- 실제 검색 측정은 고정 16개 질문을 1회 실행한다. 예상 API 호출은 질문 임베딩 16회 + 랭킹 16회다.
  실패해도 자동으로 재시도하거나 전체 캡처를 반복하지 않는다.

## 원인 진단

개선에 사용한 질문은 **dev Q02**다. 관련 공고 2건의 본문 해시·색인 존재를 확인하고,
같은 모델로 질문 1개와 해당 본문 2개를 한 요청으로 임베딩했다.
기존 벡터와 새 벡터의 cosine은 각각 약 0.999999, 0.999997로 일치에 가깝다.
현재 eligible 1,422건에 대한 정확 검색에서도 관련 공고는 각각 256위·333위였다.
본문 절단·벡터 손상보다 의미 검색 후보 20개에 포함되지 않는 문제가 확인됐다.
진단 API는 임베딩 1회·915 input tokens이며 색인을 갱신하지 않았다.

`retrieval-diagnostic.json`은 전체 정확 검색 순위와 위 검사를 보관한다. 단일 시점 관측이며
모든 저장 벡터의 생성 이력을 증명하는 전수 감사는 아니다.

## 결과 해석 규칙

- 기존 확정 라벨을 기준으로 한 후보 Recall과 최종 Recall/MRR을 나눠 비교한다.
- 새 후보 중 기존 검토 풀에 없는 공고는 **미판정**으로 센다. 무관하다고 가정하지 않는다.
- 미판정 최종 추천이 있으면 해당 질문의 오추천 여부나 무결과 성공을 확정하지 않는다.
- 양성 질문은 기존 2개뿐이다. 개선되더라도 전체 서비스 성능, 모집단 Recall, 사람 검증을 주장하지 않는다.
- heldout은 1회 확인에만 사용하며 결과를 보고 이번 구현의 규칙·라벨을 바꾸지 않는다.
- 제한시간 정렬은 장애 원인 수정이지 응답속도 개선이 아니다. API 시간과 사용자 전체 대기시간을 혼동하지 않는다.
- 이번 변경의 최종 추천은 기존 랭킹 정책 그대로다. 지원 목적 오판을 고쳤다고 주장하지 않는다.

## 방식 참고

RRF는 원점수의 단위가 다른 검색 결과를 순위로 결합한다. 이번 구현은 기존 Core 본문을 활용하므로
새 검색 서버·형태소 분석기·재색인이 필요하지 않다. [OpenSearch 공식 RRF 설명](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/)
의 1-based 공식과 기본 상수 60을 사용하며 OpenSearch 자체를 도입한 것은 아니다.

## 실제 실행 결과

`2026-09-06` 동일 스냅샷에서 16개 질문이 모두 성공했다. 상세 원본은 `capture.json`,
호출·사용량·시간은 `api-usage.jsonl`, 실행 코드·설정·파일 해시는 `execution-manifest.json`,
고정 정답 기준의 전후 비교는 `comparison.json`이다. 3단계 원본은 변경하지 않았다.

| 동일 AI 참조 기준 | 3단계 의미 검색 | 4단계 결합 검색 |
|---|---:|---:|
| 후보 pooled Recall@20 (양성 2개 질문) | 0.50 | 0.75 |
| 최종 pooled Recall@5 (양성 2개 질문) | 0.50 | 0.75 |
| 최종 MRR@5 (양성 2개 질문) | 0.50 | 1.00 |
| 무결과 예상 4개 질문의 최종 결과 | 모두 빈 목록 | 모두 빈 목록 |
| 랭킹 API 평균 응답시간 | 14.455초 | 13.600초 |

- **dev Q02:** 관련 공고 2건 중 부산 AX 에이지테크 공고 `BIZINFO:PBLN_000000000126187`을
  후보 3위로 복구했고 최종 추천은 해당 공고 1건·1위였다. 후보/최종 Recall은 `0 → 0.5`, MRR은 `0 → 1`이다.
  산업융합 규제샌드박스 사업화 공고 `BIZINFO:PBLN_000000000125904`는 여전히 누락된다.
- **heldout Q14:** 기존 관련 공고 1건은 계속 후보·최종 추천에 포함됐고 최종 1위였다. 변경 후 결과로
  이번 검색 규칙을 재조정하지 않았다. 이미 이전 보고서에 노출된 heldout이므로 새로운 독립 검증셋은 아니다.
- 기존 평가 가능 질문 **6/16개**, 양성 질문 **2개**, 제외 질문 **10개**를 그대로 유지했다.
  기존 AI 판정에 대한 일치도이며 전체 공고를 빠짐없이 판정한 Recall이나 사람 검증 점수가 아니다.
- 새 후보 320쌍 중 미판정은 **89쌍**(기존 풀에 없음 72 + 기존 unclear 17)이다.
  최종 추천의 미판정 **11쌍**(없음 1 + unclear 10)은 모두 기존 제외 질문에 속한다.
  기존 양성 2개 질문의 최종 추천에는 미판정이 없고, 무결과 예상 4개는 모두 빈 결과다.
  미판정을 무관으로 간주하거나 기존 제외 질문의 품질이 검증됐다고 주장하지 않는다.
- Q02의 과거 무관 추천 2건은 이번 최종 결과에서 빠졌지만, 프롬프트·점수 기준은 변경하지 않았다.
  후보 구성 변화와 LLM 변동성이 있으므로 **지원 목적 판단 오류를 일반적으로 해결했다는 결론은 내리지 않는다**.
- API 평균이 낮게 관측됐어도 각 버전 1회 순차 실행뿐이다. 지연시간 개선이나 운영 p95를 입증하지 않는다.
  이번 수정으로 기본 제한시간이 실측 범위와 맞게 됐다는 점을 확인했다.

검색 캡처는 OpenAI 32회(질문 임베딩 16 + 랭킹 16), 실패 응답 0회였다. 진단 1회를 포함하면
이번 작업의 프로젝트 OpenAI 호출은 **총 33회**다. 캡처 사용량은 랭킹 input 122,692 / output 31,337 /
cached input 0 tokens, 질의 임베딩 input 594 tokens다. 진단 임베딩 input 915 tokens는 별도다.
청구 금액은 조회하지 않았다. API 키·인증 헤더·DB 비밀번호·원문 응답 전체는 공유 로그에 기록하지 않았다.

## 재현 및 검증

저장소 루트에서 다음 명령으로 API 키·DB 없이 **저장된 실제 캡처의 비교 결과**를 다시 계산한다.
출력은 기존 파일 덮어쓰기를 거부하므로 이미 존재하면 새로운 출력 경로를 지정한다.

```bash
python3 -B evaluation/support-program-search/compare-captures.py \
  --fixture evaluation/support-program-search/runs/support-program-catalog-20260906-v1/review-final-v1/fixture-labeled.json \
  --before evaluation/support-program-search/runs/support-program-catalog-20260906-v1/actual-capture-v3/capture.json \
  --after evaluation/support-program-search/runs/support-program-catalog-20260906-v1/stage4-v1/capture.json \
  --reviewed-csv evaluation/support-program-search/runs/support-program-catalog-20260906-v1/review-final-v1/selected-ai-transfer-v1/reviewed.csv \
  --output /tmp/govbiz-stage4-comparison.json
cmp /tmp/govbiz-stage4-comparison.json \
  evaluation/support-program-search/runs/support-program-catalog-20260906-v1/stage4-v1/comparison.json
```

이 명령은 새로운 검색을 실행하지 않는다. 실제 검색을 다시 실행하려면 동일 DB·색인을 준비하고
[Core 평가 캡처 실행 안내](../../../../../backend/core-api/README.md)의 프로필과 별도 출력 경로를 사용한다.
manifest의 모델·제한시간·후보 수·프롬프트/코드 해시를 함께 기록해야 비교 조건을 설명할 수 있다.
기존 `verify-shared-run.py --with-capture`는 **3단계 원본 판정과 캡처**의 재현 검사이며 위 비교 명령을 대신하지 않는다.

검증 결과:

- JDK 21 `./gradlew clean test bootJar --no-daemon`: Core **291개**, 실패/오류/skip 0. MySQL 8.4 Testcontainers 포함.
- AI Service 전체 테스트 **187개** 통과.
- Frontend **114개**·lint·TypeScript·build 통과. 로컬 Node 26.7에서 실행해 프로젝트 Node 24.x 경고가 있었고 CI는 24를 사용한다.
- 평가 도구 **45개**(비교 도구 13개 포함), 기존 검토 도구 **108개** 통과.
- 명시적 라벨 스키마에서 CSV 연결 해시 누락을 거부하고, 잘못된 스냅샷·질문·중복 판정·출력 덮어쓰기를 거부한다.
- 3단계 `--with-capture` 원표 재현 검사 통과. 기존 스냅샷·정답·실패 이력은 보존했다.
- 임시 실행한 AI·MySQL·Qdrant는 종료해 작업 전 상태로 돌렸다. DB·색인·볼륨은 삭제하지 않았다.

`.env.example`과 Compose뿐 아니라 이 개발 PC의 `.env` 제한시간 3개도 `25.0 / 30.0 / 35s`로 맞췄다.
키와 DB 설정은 유지했다. `.env`는 계속 Git 제외이며 다른 개발자는 자신의 짧은 override가 남아 있지 않은지 확인한다.

## 남은 4단계 작업

**4단계 1차 개선·재측정 완료**이며 4단계 전체가 끝난 것은 아니다.

1. 후보에 있는 공고를 잘못 추천하는 지원 목적 판단을 dev 사례로 분리해 검증한다. 이번 MRR 상승만으로
   AI 판단 개선을 완료 처리하지 않는다. 누락된 나머지 관련 공고 1건도 알려진 한계로 유지한다.
2. 추가 품질 개선 때 필요하면 새 미판정 쌍을 AI-only 방식으로 판정하되, 지금의 고정 비교 결과는 보존한다.
   점수를 높이기 위해 질문·정답·제외 대상을 바꾸지 않는다.
3. 외부 공개 전 요청량·동시 실행 제한과 운영 지연시간·실패율·토큰 관측을 추가한다.
   이번 로그는 단일 평가 실행의 관측이며 상시 운영 모니터링이나 부하 테스트를 대신하지 않는다.
