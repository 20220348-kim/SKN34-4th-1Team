# 4단계 2차: 동일 후보에서 지원 목적 판단 개선

## API 실행 전에 고정한 실험 계획

- 기준 코드: `0481abb`, 입력 후보: `../stage4-v1/capture.json`의 질문별 20건.
- 스냅샷 1,422건, 질문 16개, 기준일 2026-09-06, 기존 AI-only 정답·제외 질문을 유지한다.
- 설계에는 dev Q01–Q10의 기존 오추천만 사용한다. heldout은 회귀 확인만 하고 결과를 보고 재튜닝하지 않는다.
- 변경 변수는 프롬프트의 지원 목적 채점 지침뿐이다. 지역·업종·공고 ID별 예외를 추가하지 않는다.
- 모델 Luna, reasoning none, 출력 최대 4,000 tokens, 점수 계약 v3, semantic 20/total 60 기준,
  최대 추천 5건, 모델/Agent 제한시간 25/30초, SDK 재시도 0회는 유지한다.
- old/new 각각 16회, 총 32회 랭킹 API를 한 번씩 호출한다. 질의 순서마다 before/after 실행 순서를 교대한다.
  임베딩은 호출하지 않고 실패 시 자동 재시도하지 않는다. 응답을 다른 변형의 입력으로 넘기지 않는다.
- 실제 production HTTP route → Service → Agent → OpenAI → Response 흐름을 ASGI로 호출한다.
  새로운 전체 검색 캡처나 브라우저 응답시간 측정으로 취급하지 않는다.

## 입력의 동일성

원본 캡처에는 질문·후보/최종 ID·메타데이터가 있지만 구조화된 HTTP 요청 본문은 없으므로,
원래 HTTP payload의 바이트 자체를 복구했다고 주장하지 않는다.
기존 Core JAR의 Repository와 Ranking Facade/Mapper를 사용하여 현재 DB에서 요청을 복원했다.
MySQL 세션은 읽기 전용이며, 전체 1,422건의 색인 본문·해시·정렬 값·카탈로그 지문이 고정 스냅샷과
일치할 때만 출력했다. 네트워크 Client 대신 요청을 저장한 뒤 즉시 종료하는 대역을 사용했으며 외부 API는 0회다.
공유한 `requests.json`의 전체 내용과 순서를 두 변형에 똑같이 전송하고 정규화된 요청 해시도 보관한다.

## 채택 기준

동시기에 재실행한 before와 after를 비교하며 과거 실행보다 좋아 보이는 것만으로 채택하지 않는다.

1. dev에서 기존 AI 판정상 무관한 최종 추천 수가 감소해야 한다.
2. dev에서 기존 AI 판정상 관련 있는 최종 추천 수는 감소하지 않아야 한다.
3. before가 관련 공고를 1위로 반환한 dev 질문은 after에서도 관련 공고를 1위로 반환해야 한다.
4. 기존 공식 양성 Q02·Q14의 최종 Recall/MRR이 나빠지지 않아야 한다.
5. 기존 무결과 Q09·Q10·Q15·Q16은 계속 빈 목록이어야 한다.
6. 32회 모두 API·응답 계약 검증을 통과해야 한다.

하나라도 실패하면 production 프롬프트 변경을 채택하지 않고 실험 자료만 남긴다.
부적절한 추천 감소와 함께 관련 공고까지 줄어드는 결과를 개선으로 포장하지 않는다.
실행 결과를 보고 같은 heldout으로 반복 조정하지 않는다.

## 해석 한계

기존 5개 AI 판정의 합의를 참조할 뿐 사람이 검증한 정답은 아니다. 미판정·unclear는 무관으로 세지 않는다.
제외 질문 10개는 공식 평가에 복귀시키지 않으며, 이미 판정한 후보 쌍의 진단 지표만 별도로 계산한다.
각 변형 1회 측정이므로 통계적 우월성·전체 검색 품질·운영 지연시간을 입증하지 않는다.
공식 양성 질문이 2개뿐이라는 한계도 그대로 유지한다.
