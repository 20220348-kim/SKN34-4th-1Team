# 3단계: AI-only 실데이터 검색 1차 평가

**실제 검색 실행·판정 병합·지표 계산·재현 가능한 보고서 작성까지 완료했다. 검색 품질이 충분하다는 합격 판정은 아니다.**
고정 질문 16개를 전부 실행했지만, AI 합의 기준으로 점수를 낼 수 있는 질문은 **6개(37.5%)**뿐이다.
그중 관련 공고가 있는 질문은 **2개**이므로 아래 Recall·MRR을 서비스 전체 정확도로 표현하면 안 된다.
처음 요구했던 폭넓은 대표 질문 평가나 사람이 검증한 정답 세트까지 갖춰졌다는 의미도 아니다.

## 고정 조건과 판정 출처

| 항목 | 이번 결과 |
| --- | --- |
| 기준일 / 제공처 | 2026-09-06 / 기업마당 |
| 현재 공고 / 접수 중 평가 공고 | 1,506건 / 1,422건 |
| 실제 검색 | 16/16 성공, 후보 각 20개·최종 최대 5개 |
| 질문 분할 | 실행 전 고정한 dev 10개 / heldout 6개 유지 |
| 최종 검토 풀 | 질문·공고 쌍 570개 = 기존 321개 + 새 검색 후보 249개 |
| AI 원표 | 기존 1,605표 + 과거 한 차례 재검토 210표 + 신규 1,245표 = 누적 3,060표 |
| 최종 판정 | 합의 541개(관련 28 / 무관 513), 미확정 29개 |
| 판정 방식 | AI-only, 실제 사람 확인 0개 |
| 평가에 사용한 질문 | 관련 공고 있음 2개 / 풀에서 관련 공고 없음 4개 |
| 제외 질문 | 10개(62.5%), 0점이나 무결과로 바꾸지 않음 |

신규 249쌍은 과거 원표·재검토와 다른 **새 Luna 작업 5개**가 같은 정책으로 독립 판단했다.
다른 심사자의 답, 검색 순위·점수는 전달하지 않고 고정 질문과 공고 요약만 전달했다. 프로젝트 API 키는
신규 판정에 사용하지 않았다. 4/5 이상 같은 확정 판정일 때 채택하여 신규 합의 238개·미확정 11개가 생겼다.
기존 미확정 18개와 원표는 그대로 보존했고, 합의를 얻기 위한 재판정은 하지 않았다.
기존 대화의 사람 판정 2개는 별도 원본으로 보존하지만 이번 AI-only 정답에는 섞지 않았다.

## 후보 검색과 최종 추천 지표

아래는 **검토 풀의 AI 합의 참조 기준과 비교한 값**이다. 전체 1,422개 공고를 질문별로 전수 판정한 Recall이 아니다.
Recall은 알려진 관련 공고 중 찾아낸 비율, MRR은 첫 관련 공고가 얼마나 앞에 있는지 나타내는 값이다.
질문별 값을 평균했으며, 무결과 질문은 Recall·MRR 분모에서 빼고 별도 오추천율로 계산한다.

| 항목 | 전체(진단 요약) | dev(개선용) | heldout(최종 확인용) |
| --- | --- | --- | --- |
| 전체 / 평가 / 제외 질문 수 | 16 / 6 / 10 | 10 / 3 / 7 | 6 / 3 / 3 |
| 관련 공고 있는 질문 수 | 2 | 1 | 1 |
| 풀에서 관련 공고 없는 질문 수 | 4 | 2 | 2 |
| 후보 Recall@20 | **0.50** | 0.00 | 1.00 |
| 최종 추천 Recall@5 | **0.50** | 0.00 | 1.00 |
| 최종 추천 MRR@5 | **0.50** | 0.00 | 1.00 |
| 무결과 질문에 후보 반환 | 4/4 | 2/2 | 2/2 |
| 무결과 질문에 최종 오추천 | **0/4** | 0/2 | 0/2 |

heldout의 1.00은 **양성 질문 한 개에서 공고 한 개를 찾은 결과**다. “검증 정확도 100%”라고 홍보할 수 없다.
후보 단계는 비슷한 20개를 넓게 가져오므로 무관 질문에도 후보가 생겼지만, 이번 무관 질문 4개는 최종 추천에서
모두 제거됐다. 후보 반환율과 사용자에게 보이는 최종 오추천율을 혼동하지 않는다.

기계 판독 보고서: [전체](report-all.json) / [dev](report-dev.json) / [heldout](report-heldout.json).
참고용 최신순·키워드 기준의 전체 Recall@20은 각각 0.25·0.75다. 표본이 두 양성 질문뿐이므로
키워드 방식의 일반적인 우월성이나 하이브리드 개선 효과까지 증명한 결과는 아니다.

## 확인된 실패와 성공

### dev Q02 — 관련 공고를 후보에서 놓침

질문은 “부산에서 고령친화 기술 서비스를 만드는 중소기업인데 시장 검증과 사업화 비용을 지원받고 싶어”다.
AI 참조의 관련 공고 `BIZINFO:PBLN_000000000125904`와 `BIZINFO:PBLN_000000000126187`이 모두 후보 20개에 없었다.
특히 후자는 **부산 AX 에이지테크 시장확산 지원사업**으로, 요약에 부산 에이지테크 기업의 사업화·시장진출
지원이 명시돼 있다. 최종 점수화를 잘하더라도 들어오지 않은 공고를 복구할 수 없으므로 후보 검색 진단이 필요하다.

최종 추천은 해양산업 기술 지원 `BIZINFO:PBLN_000000000126166`과 수출입 애로 바우처
`BIZINFO:PBLN_000000000122227`이었다. 이 두 공고는 최종 AI 참조에서 무관 판정이다.
따라서 **후보 누락뿐 아니라 질문의 지원 목적·분야를 벗어난 최종 추천도 관찰됐다.**
정확한 후보 누락 원인(임베딩 입력·색인 생성 이력·검색 점수 등)은 이번 측정만으로 확정하지 않는다.

### heldout Q14 — 후보와 최종 추천 모두 성공

부산 사상구 소상공인의 대출 보증료 지원 질문에서 `BIZINFO:PBLN_000000000117071`을 찾아
최종 1위로 반환했다. 이 사례는 최종 확인 결과로만 기록하고 이 질문에 맞춘 조건이나 프롬프트를 추가하지 않았다.

### 평가 제외 — 어려운 사례가 빠졌다는 한계

제외 질문은 **Q01·Q03·Q04·Q05·Q06·Q07·Q08·Q11·Q12·Q13**이다. 미확정 공고가 한 개라도 있는 질문은
전체를 제외하는 기존 규칙을 유지했다. 새로운 후보를 검토하면서 Q01·Q06에도 미확정 항목이 드러나,
사전 풀의 평가 가능 8개가 최종 풀에서는 6개로 줄었다. 기존 판정이 삭제되거나 실행에 실패한 것이 아니다.
제외된 질문에서 반환된 추천은 캡처에 그대로 남아 있지만 이번 숫자로 적합성을 보증하지 않는다.

## 응답시간과 운영 준비 상태

성공 실행에서 추천 OpenAI API 응답은 평균 **14.455초**, 최소 10.874초·최대 19.195초였다.
평가용 모델/Agent/Core 제한시간은 25/30/35초였고 운영 기본값 8/10/12초는 바꾸지 않았다.
**모든 관측 추천 응답이 기본 모델 제한 8초를 넘었다. 현재 기본 설정의 안정성을 통과했다고 볼 수 없다.**
단일 순차 실행이므로 사용자 화면 전체 지연·동시 요청·p95·장기 실패율도 아직 검증하지 않았다.

## 다음 단계: 측정에서 드러난 문제부터 개선

1. **응답시간과 제한시간을 먼저 정리한다.** 화면에서 허용할 대기시간을 정하고 모델·Agent·Core 제한을
   일관되게 맞춘 뒤 실제 경로에서 검증한다. 제한시간 연장만으로 응답속도가 개선됐다고 기록하지 않는다.
2. **dev Q02의 후보 누락 원인을 진단한다.** 실제 색인의 생성 이력·입력 본문·유사도 결과를 확인한 뒤,
   필요할 때만 키워드 결합 등 하나의 개선을 비교한다. 지역·업종별 예외 조건을 무작정 추가하지 않는다.
3. **최종 추천의 지원 목적 불일치를 확인한다.** 후보 개선 전후와 AI 점수화 개선 전후를 분리 측정한다.
   점수 합산 코드를 바꾸거나 정답 ID를 강제로 추천하지 않는다.
4. **더 강한 품질 주장이 필요할 때 평가 범위를 넓힌다.** 새 버전의 질문·라벨을 별도로 만들거나 사용자가
   원할 때 혼합/사람 검토로 바꾼다. 이번 미확정을 부적합으로 바꿔 점수를 올리거나 현재 heldout에 맞춰 튜닝하지 않는다.

이번 3단계는 **제한적인 AI-only 기준선 측정**으로 마무리하고, 다음 구현은 4단계의 측정 기반 개선이다.
사람 검토는 현재 방식의 필수 작업이 아니다. 다만 6개 질문만의 결과를 전체 서비스 성능 검증 완료로 취급하지 않는다.
AI 심사자와 추천 모델은 같은 모델 계열이므로 오류가 상관될 수 있고, 다수결은 정답 확률이 아니다.

## 다른 개발자가 API 없이 재현하기

저장소 루트에서 Python 3.11 이상으로 실행한다. API 키·MySQL·Qdrant·Excel은 필요하지 않다.

```bash
python3 -B evaluation/support-program-search/review/verify-shared-run.py \
  --run-dir evaluation/support-program-search/runs/support-program-catalog-20260906-v1 \
  --with-capture
```

기존·재검토·추가 원표를 검증하고, 임시 디렉터리에서 최종 풀·선택·라벨·세 지표 보고서를 다시 만들어
저장된 결과와 비교한다. 원본을 덮어쓰거나 모델을 재실행하지 않는다. 누락·변조된 자료는 실패한다.
숫자만 다시 보고 싶다면 다음 명령의 `all`을 `dev` 또는 `heldout`으로 바꿀 수 있다.

```bash
RUN=evaluation/support-program-search/runs/support-program-catalog-20260906-v1
python3 -B evaluation/support-program-search/evaluate.py \
  --fixture "$RUN/review-final-v1/fixture-labeled.json" \
  --capture "$RUN/actual-capture-v3/capture.json" --split all
```

고정 자료로 계산이 재현된다는 것과 모델을 다시 호출했을 때 같은 순위가 나온다는 것은 다르다.
새 검색 실행은 동일 스냅샷·설정·모델을 준비하고 새 캡처 버전에 기록한다. 실패 이력과 이 기준선을 덮어쓰지 않는다.
