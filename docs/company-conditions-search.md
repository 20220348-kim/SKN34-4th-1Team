# C01 — 익명 기업 조건 검색

[문서 목록](README.md) · [API 계약](support-program-search-contract.md) · [개발 전략](development-strategy-20260907.md)

기준일: 2026-09-07. 사용자 승인 범위는 다음 기능의 첫 단계인 **기업 조건을 직접 입력하고 검색에 적용하는 흐름**이다.
자연어로 조건을 자동 갱신하는 C02나 전체 기획서 구현을 완료했다는 의미는 아니다.
작업 시작 기준 커밋은 `46526c0`이며, 이 문서는 그 이후의 C01 변경만 다룬다.

후속 원문 우선 자격 검토는 [랭킹 v4 수정 기록](source-first-eligibility-review.md)에 별도로 정리한다.
아래 테스트 수치·컨테이너 ID는 최초 C01 반영 당시 기록이며 v4 검증·배포 결과가 아니다.

현재 UI에서는 아래 C01의 수동 입력·적용/초기화·조건 칩·접수 상태 선택 조작을 제거했다. 조건 변경·해제는
대화의 제안 확인 방식으로 유지하며, [현재 화면 안내](../frontend/web/README.md#화면과-현재-동작)와
[대화 조건 계약](conversation-condition-update.md)을 따른다. 아래 최초 구현·검증 기록은 보존한다.

## 구현 범위

- 현재 소재지·업종·설립일·지원 목적을 선택적으로 입력한다. 모르는 항목은 비워둘 수 있다.
- 사용자가 `조건 적용`을 눌러 확인한 값만 검색에 사용한다. 적용 조건 표시·수정·개별 해제·전체 초기화를 제공한다.
- 접수 중/전체를 선택한다. 전체는 예정·마감·상태 미확인 공고를 포함하지만 상태를 임의로 바꾸지 않는다.
- 새 검색에도 직접 적용한 조건은 유지하며 각 검색에 당시 조건을 표시한다. 이후 수정으로 과거 결과의 조건이 바뀌지 않는다.
- 검색 중에는 조건 조작을 막고 기존 취소·시간 초과·늦은 응답 무시 동작을 유지한다.
- 조건은 Redux 메모리에만 둔다. 새 대화 또는 브라우저 새로고침 시 초기화되며 로그인·DB·localStorage 저장은 없다.

## 실제 호출 흐름

`Web → POST /api/v1/support-programs/search → Core Controller → Search Service`

Search Service는 MySQL의 현재 검색 가능 공고에 기존 접수 상태 필터를 적용한 뒤:

1. 후보 검색: 원래 검색문과 입력 조건·서버 서울 날짜를 포함한 내부 검색문으로 의미·키워드 검색을 실행한다.
2. 최종 추천: 원래 검색문과 구조화된 조건을 분리해 기존 Ranking Facade·Client에 전달한다.
3. AI 점수화: `HTTP API → Service → Agent → OpenAI → Response`. 기존 Agent의 한 번의 호출에 조건 해석 지침을 추가한다.

새 LLM·외부 서비스·production 의존성·DB migration은 추가하지 않는다. 검색 조건이 없는 GET·기존 평가 경로와
500 UTF-16 공개 검색문 제한은 유지한다. 자세한 필드/문자/날짜 규칙은 [API 계약](support-program-search-contract.md)에 있다.

## 판단·개인정보 경계

- 미입력 조건은 적합이 아니다. 회사 정보나 공고 근거가 부족하면 내부 자격 판정은 `UNKNOWN`으로 남겨야 한다.
- 현재 소재지를 이전 예정으로 추정하지 않는다. 공고의 지역 예외·업력 기준일·제외 조건을 구분한다.
- 공고의 불완전한 지역·업종 문자열만 비교해서 후보를 강제 제외하지 않는다. 조건은 검색·AI 판정에 반영되며 자격을 보증하지 않는다.
- 검색문과 적용 조건이 명백히 충돌하면 적용 조건을 우선한다. 검색문을 썼다는 이유로 폼 값을 자동 변경하지 않는다.
- 조건은 URL에 넣지 않고 POST body로 전송한다. 다만 추천을 위해 AI Service 및 기존 OpenAI 요청에는 포함되므로,
  사용자는 검색에 불필요한 개인정보·비밀정보를 입력하지 않아야 한다. 기존 `store=False`·tracing 비활성은 유지한다.
- 최초 C01에서는 후보마다 원문을 새로 수집하거나 조건별 조항 대조표를 만들지 않았다. 후속 v4에서는
  기존 API 본문을 이용한 대상·지역 검토와 인용·확인 필요 표시를 추가하며, 첨부 전체 대조는 여전히 미지원이다.
  추천 점수는 선정 확률이 아니다.

Core는 사용자가 **이번 C01 검증에 한해 Docker 소켓 연결을 명시적으로 승인**한 뒤 테스트했다.
Temurin JDK `21.0.12+8`, MySQL `8.4.11`에서 `./gradlew clean test --no-daemon`을 실행했고
`BUILD SUCCESSFUL in 4m41s`, 7개 task 실행을 확인했다. 테스트 제외 필터·init script·대체 DB를 사용하지 않았다.
첫 실행은 빌드 폴더 정리에서 실패했지만, 동일 명령 재시도는 clean부터 전체 테스트까지 통과했다.
호스트 JDK 시도는 Gradle 배포물 다운로드의 환경 네트워크 제한으로 실행되지 못해 Linux 테스트 컨테이너를 사용했다.
최신 XML 시각은 `2026-09-07T05:34:53.359Z`~`05:37:23.775Z`이며 최종 합계를 별도로 다시 집계했다.

검증용 runner·MySQL·Ryuk 컨테이너는 자동 정리됐고, 기존 개발 서비스 5개는 같은 ID와 실행 상태를 유지했다.
기존 전용 Gradle 캐시 볼륨은 유지했다. 이 검증에서 실제 OpenAI·공공 API 유료 호출은 없었으며,
DB migration·Mapper SQL·Repository·production 의존성은 변경하지 않았다.

브라우저 검증은 별도 loopback Vite(5178)와 가상 HTTP 응답(18081)을 사용했다. 실제 사용자 기업정보·운영 DB·유료 API를
사용하지 않았다. 이 검증은 실제 브라우저와 Frontend HTTP 전송을 확인하며, 실제 모델의 판단 품질을 증명하지 않는다.

- 네 필드 입력·적용 후 POST body의 조건과 공개 검색문이 분리되어 전달됨을 확인.
- 지역만 서울→부산으로 수정하고 업종을 해제한 뒤, 새 요청에서 해당 값만 변경·제거됨을 확인.
- 전체 접수 상태 선택 시 `acceptingOnly=false` 전달 및 결과 안내 문구 변경 확인.
- 이전 검색 당시 조건은 서울/업종을 유지하며 이후 변경된 부산/업종 미입력 조건과 구분됨을 확인.
- 미래 설립일 입력 거부와 기존 적용 조건 보존 확인.
- 전체 초기화 후 조건 없는 검색, 새 대화 초기화, 새로고침 후 조건 휘발 확인.

브라우저 확인 후 임시 탭과 검증용 서버를 종료했고 5178·18081 포트에 남은 listener가 없음을 확인했다.
이 최초 검증 단계에서는 기존 개발 Compose 서비스를 재빌드하지 않았다. 이후 사용자가 로컬 재빌드·재시작을
승인하여 아래와 같이 반영했다. 운영 환경 배포는 수행하지 않았다.

### 후속 로컬 실행 반영 — 2026-09-07

Web은 소스 bind mount로 POST 검색을 즉시 사용했지만, 기존 Core·AI 이미지는 갱신되지 않아 Web 경유 검색이
405를 반환했다. 당시 Core의 `Allow`는 `GET,HEAD,OPTIONS`였고 AI 명세에는 `companyConditions`가 없었다.

사용자 승인 후 기존 `.env`의 Core·AI 환경값이 실행 컨테이너와 같은지 비밀값 출력 없이 비교하고 두 이미지만
재빌드했다. Core는 기존 Dockerfile로 성공했다. AI는 기존 uv 캐시의 FastAPI RECORD와 Pydantic metadata
오류로 실패하여 임시 Dockerfile의 두 `uv sync`에 `--no-cache`를 추가해 해결했다. 같은 버전·잠금 파일·해시 검증을
유지했으며 production Dockerfile·의존성 파일은 변경하지 않았다. FastAPI 캐시만 재다운로드 가능한 범위에서
정리했고 공유 캐시 전체를 삭제하지 않았으므로, 다른 손상 캐시를 사용하는 후속 일반 빌드에서는 오류가 재발할 수 있다.

AI를 먼저 `--no-deps --no-build --pull never`로 교체하고 API 기동을 확인한 뒤 Core를 같은 방식으로 교체했다.

| 항목 | 확인 결과 |
|---|---|
| Core 컨테이너 | `1b5f367bb697` 실행, 새 이미지 `71c984138fd9` |
| AI 컨테이너 | `0b3fe84592ba` 실행, 새 이미지 `6f3cc31b8f7d` |
| Core 검색 OPTIONS | `Allow: POST,GET,HEAD,OPTIONS` |
| Web 경유 빈 JSON POST 검색 | 405가 아닌 400 `REQUEST_VALIDATION_FAILED`. 입력 검증에서 거부하며 실제 검색은 실행하지 않음 |
| Web 경유 Core·AI Health | 각각 200 및 `status=up` |
| AI 명세 | 기업 조건 4개와 필수 `referenceDate`, 내부 검색문 최대 1,000 확인 |
| 검색 준비 상태 | `SEARCHABLE`, `indexReady=true`, 공고 1,503건(확인 시점 기준) |
| 유지 자원 | MySQL `505a1af7beec`, Qdrant `7c0e50e0ebe7`, Web `b529a34d6ed1`. DB·벡터 volume 초기화 없음 |

추가 유료 검색은 실행하지 않았다. 재시작 후에는 기존 설정의 자동 수집·색인이 동작할 수 있으며,
위 Health·명세·준비 상태 확인은 실제 모델 검색의 성공·품질 검증을 대신하지 않는다.

## 후속 범위

기업 단계·소재지 이전 계획의 별도 입력, C02 후속 발화로 조건 갱신, E01 조건별 근거·확인 질문, 회원 인증·영구 프로필,
북마크·알림은 이번 범위가 아니다. 사람 검토 평가(Q01)와 조건 검색의 실제 후보 누락·오추천 측정도 별도 진행해야 한다.
