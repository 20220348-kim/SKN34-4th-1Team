# GovBiz 기획 정합성·경쟁 전략·개발 백로그

[문서 목록](README.md) · [현재 구현](implementation-status.md) · [이번 추가 버그 검수](project-review-20260907.md)

기준일: 2026-09-07. 기획 기준은 [사업 기획서 v3](govbiz-business-plan-v3.pdf), 2026-08-30이다.
코드·기존 평가 기록·국내 서비스 공식 공개 자료를 대조했다. 이 문서의 **개발 제안·목표 수치는 아직 구현되거나 달성된 결과가 아니다.**
경쟁사 유료/로그인 기능의 실제 정확도·알림 전달률·사업 성과는 테스트하지 않았다.

후속 구현: 아래 표는 최초 전략 수립 시점의 진단이다. 이후 사용자 승인으로 C01 중
**지역·업종·설립일·지원 목적의 익명 입력·적용·검색 반영과 접수 중/전체 선택**을 구현했다.
[현재 구현·검증 범위](company-conditions-search.md)를 우선 참고한다. 이후
[공식 API 본문 우선 자격 검토](source-first-eligibility-review.md)에서 대상·지역별 인용과 확인 필요 분리를 구현했다.
후속 [C02 대화 조건 갱신](conversation-condition-update.md)에서는 작은 확정 상태·새 메시지의 변경 제안과
사용자 확인 검색을 구현했다. 아래 최초 진단 표와 구분해 후속 문서의 구현·검증 결과를 확인한다.
기업 단계 구분·첨부 전체 자격 대조·사람 검토 품질 게이트가 남아 있으므로
C01/E01 전체나 기획서 전체 완료로 표시하지 않는다.

후속 UI 간소화로 C01 계획의 수동 조건 폼·조건 칩 해제·접수 상태 선택 상자는 제거했다. 조건 변경·해제와
접수 전체 요청은 대화의 제안 확인 방식으로 유지한다. 아래 최초 계획은 보존하며, 현행 화면은
[Frontend 안내](../frontend/web/README.md#화면과-현재-동작)와 [C02 현재 흐름](conversation-condition-update.md)을 우선한다.

## 1. 결론과 범위

현재 GovBiz는 **기업마당 공고 검색과 단일 공고 HTML 근거 질문을 검증할 수 있는 기술 MVP**다.
기획서의 **기업정보 → 대화로 조건 좁히기 → 근거 확인 → 저장 → 신청 준비**가 연결된 제품 MVP는 아직 아니다.
기술 기반을 다시 만들지 말고, 이미 있는 검색·원문·저장소 위에 빠진 사용자 흐름을 순서대로 완성한다.

- 유지: MySQL 정기 수집, 공개 전 색인, 제공처별 실패 격리, 하이브리드 후보 검색, 공식 원문 인용, 명시적 오류, 회귀 평가 도구.
- 최우선 제품 공백: 구조화된 기업 조건, 후속 질문의 조건 유지, 일치/불일치/정보 부족의 사용자 공개, 다음 확인 질문.
- 다음 완성 범위: 실제 두 번째 제공처, 첨부문서 근거, 비교·체크리스트, 사용자별 저장·마감 관리.
- 차별화 가설: **“맞춤 추천” 자체가 아니라, 회사 조건과 공고 조항을 대조한 검토 기록을 근거·불확실성·다음 행동까지 연결한다.** 경쟁사에 없는 독점 기능이라고 주장하지 않는다.
- 보류: 선정 확률, 자동 신청, 사업계획서 전면 자동 작성, 투자·조달·개인 복지 확장, 과금, MCP, 범용 멀티에이전트 프레임워크.

이번 작업은 확인된 버그 수정과 실행 전략 수립이다. 아래 신규 제품 기능, 실제 사용자 모집, 외부 알림 발송, 새 API 활용신청, 유료 모델 평가를 일괄 실행한 것이 아니다.

## 2. 기획서 요구사항 추적

`부분`은 관련 코드가 있지만 기획의 최종 사용자 동작을 충족하지 못한다는 뜻이다. 화면 존재·테스트 개수로 기능 완료율을 계산하지 않는다.

| 기획 요구 | 현재 판정 | 코드로 확인한 구현과 차이 | 연결 백로그 |
|---|---|---|---|
| 통합 공고 탐색, p.3·7·10·11 | 부분 | 기업마당 실제 수집 구현. 제공처별 readiness·복합 식별자·부분 검색은 있으나 K-Startup은 URL/미지원 안내 준비만 있음. 제공처 간 동일 사업 묶기도 없음 | D01, D02, D04 |
| 기업 맞춤 추천, p.3·4·6 | 부분 | 질의와 공고 후보를 점수화. 기업 프로필 입력·저장·사용자가 확인한 조건 계약은 없음. 접수 상태 외 구조화 필터를 먼저 적용하는 흐름도 미완성 | C01, C02, E01 |
| 대화형 탐색, p.3·4·9·10 | 미구현 | 채팅 UI/메모리 메시지는 있으나 다음 검색에 현재 질의만 전달. “지원금 위주”가 앞선 서울·업력 조건을 이어받지 않음 | C01, C02 |
| 추천 이유와 근거, p.3·5·9 | 부분 | 추천 이유·점수, 기업마당 HTML 근거 질문·인용 구현. 내부 자격 판정이 있어도 공개 응답은 조건별 판정/조항 대조표가 아님. 추천과 근거 질문이 분리됨 | E01, D03, Q01 |
| 관심 공고·마감 관리, p.3·5 | 미구현 | 사용자별 관심 공고·메모·검토 상태·마감/변경 알림 없음. 동기화 내용 해시는 사용자 변경 이력이 아님 | U01, U02, U03 |
| 공고 비교·신청 준비, p.3·5 | 미구현 | 상세는 있으나 2~3건 동일 기준 비교, 원문 기반 필요 서류·체크리스트 없음 | W01, W02 |
| 정기 수집·변경 검증·DB 검색, p.8·10 | 기본 구현 | 전체 페이지/건수 검증, UPSERT, 공개 전 벡터 준비, 실패 시 기존 데이터 보존. 다중 인스턴스 중복 작업·오래된 벡터 정리·운영 복구 실증은 남음 | O01, D01, D04 |
| 없는 정보를 추측하지 않음, p.4·8·9 | 부분 | 근거 부족 응답과 계약 검증은 있음. 의미상 자격 오판·조건 누락이 없다는 보장은 아니며 사람 검증 정답/다중 청크 평가 부족 | Q01, E01, D03 |

중요한 해석: 기획서 p.3·5는 저장·알림을 핵심 흐름으로 약속하지만 p.10은 저장 프로필·변경 추적을 선택 확장으로 둔다.
이를 숨기지 않고 **익명 조건 입력·대화·근거를 첫 릴리스, 영구 저장·알림을 후속 제품 완성 릴리스**로 나눈다.
저장·알림을 보류한 버전을 “기획서 전체 구현 완료”라고 부르지 않는다.

## 3. 국내 경쟁군에서 가져올 것과 가져오지 않을 것

아래는 2026-09-07 확인한 공식 공개 페이지의 기능 설명이다. 표시 공고 수·홍보 성과·추천 정확도를 별도로 검증한 것은 아니다.
공개 검색/공고 페이지와 서비스 안내가 운영되는 것은 확인했지만 개인화 기능의 실제 사용 경험을 대신하지 않는다.

| 경쟁 서비스 | 확인한 기능/출처 | GovBiz에 반영할 전략 | 그대로 따라 하지 않을 것 |
|---|---|---|---|
| 웰로비즈 | 기업정보 불러오기, 조건 필터·저장, 매칭 키워드. [공식 상세검색 업데이트](https://www.wellobiz.com/guest/insights/270). 관심사업·일정·알림·첨부 요약 안내. [공식 기능표](https://www.wellobiz.com/guest/price) | 프로필과 검색 조건을 연결하고 사용자가 적용 조건을 수정 가능하게 한다. 저장·마감 관리는 제품 기본 흐름으로 편성 | 조달·투자·증명서 발급까지 한 번에 확장 |
| 지원매치 | 매칭 이유·등급별 확인 필요 구분, 준비 체크리스트·AI 작성 안내. [공식 FAQ](https://jiwonmatch.com/faq) | 점수만 보여주지 않고 부족 정보·제외 가능 조건·준비 작업을 분리 | 등급이나 점수를 검증된 신청 가능성/선정 확률로 해석 |
| PlanScore | 회사 상황을 문장으로 입력하는 AI 검색과 기관별 공개 공고 목록. [공식 공고 검색](https://www.planscore.kr/programs) | 자연어 검색은 기본 기대치. 검색 후 “내 조건과 어느 조항이 연결되는가”를 더 깊게 구현 | 자연어 입력창만으로 차별화됐다고 홍보 |
| SeedUp | 아이디어 입력 → 대화 → Lean Canvas → 맞춤 공고·초안, 알림 안내. [공식 서비스 소개](https://seedup.co.kr/) | 초기 온보딩을 짧은 대화로 만들고, 탐색 결과를 준비 행동으로 연결 | 아이디어 구체화·문서 전체 생성까지 초기 핵심 범위를 확대 |

**전략적 추론:** AI 추천·챗봇·요약·알림은 이미 경쟁군의 제안에 포함되어 있다. GovBiz는 이 기능들을 없애서 차별화하는 것이 아니라,
한정된 초기 고객에게 필요한 기본 흐름을 채운 뒤 **조건-조항 대조의 검증 가능성**과 **부족 정보의 명시성**을 사용자 평가로 입증해야 한다.

첫 검증 고객은 기획서 p.6 중 **지원사업 전담자가 없는 초기 창업기업의 대표/실무자**로 좁히는 안을 권한다.
이는 검증된 시장 결론이 아니라 범위를 줄이기 위한 가설이다. 첫 인터뷰에서 수요가 다르면 수정한다.

## 4. 우선순위 규칙

- **P0:** 기존 기능의 오류/데이터 손상 방지, 핵심 대화·근거 계약, 품질 검증. 초기 제품 릴리스 전 필수.
- **P1:** 기획 핵심 흐름을 완성하는 기능. 단계적으로 배포하되 빠진 범위를 사용자에게 명시.
- **P2:** 기본 흐름 사용 효과를 확인한 뒤 투자하는 확장/운영 최적화.
- 인증·정보 보호·백업 등은 데모에선 미구현으로 표시할 수 있지만, 실제 사용자 정보 저장·외부 베타를 시작하는 시점에는 필수 게이트다.
- 우선순위를 숫자화한 가짜 시장성 점수로 정하지 않는다. 기획 필수성 → 사용자 오판 위험 → 선행 의존성 → 검증 비용 순으로 판단한다.

역할 표기: FE=Frontend, Core=Core API, AI=AI Service, QA=평가·검증 담당, PO=기획 책임자.
역할은 기존 팀원이 겸임할 수 있다. 인원·남은 기간이 확정되지 않았으므로 달력 일정과 확정 공수는 약속하지 않는다.

## 5. 실행 가능한 개발 백로그

모든 미완료 항목은 **제안 상태**다. 최초 버그 수정은 [별도 검수 기록](project-review-20260907.md),
이후 승인된 C01 최소 구현은 [기업 조건 검색 기록](company-conditions-search.md)에서 완료·검증 범위를 구분한다.

### P0 — 신뢰 가능한 대화형 탐색

## 7. 품질 게이트 — 목표와 현재 측정을 분리

### 현재 알 수 있는 것

- [검색 기준선/개선 기록](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/README.md)은 AI-only 참조이며 사람 검증 정답이 아니다.
- 고정 후보 프롬프트 비교에서 held-out 무관 선택 5건이 그대로 남았다. 개발 세트 개선으로 전체 품질이 좋아졌다고 결론 내리지 않는다.
- [최신 공식 HTML 평가](../evaluation/support-program-evidence/runs/official-flow-20260907-v2/README.md)는 소규모·단회 AI 의미 검토다. 공식 공고당 청크가 1개라 다중 청크 검색 성능을 입증하지 못한다.
- 코드 테스트는 식별자·계약·예외·상태 전이를 검증한다. 테스트가 전부 통과해도 이유 문장의 사실성·자격 정확도가 증명되는 것은 아니다.

### 제안 평가 프로토콜

1. **데이터 고정:** 최소 100개 질문을 목표로 dev 60 / 새 held-out 40을 사전 분리. held-out에는 관련 공고 존재 20, 무결과 10, 정보 부족 10을 포함하도록 구성한다. 시나리오·기업 조건·공고 스냅샷·기준일·원문/첨부 해시를 보존한다. 이는 초기 목표 표본이며 모집단 대표성이나 통계적 확증은 아니다.
2. **판정 분리:** 사람이 원문을 대조하고 held-out은 2인 독립 판정 후 불일치 조정. AI 보조 라벨은 출처를 남기고 사람 정답으로 둔갑시키지 않는다. 검토 인력이 없으면 품질 승인 미완료로 남긴다.
3. **분모 정직성:** 시스템 후보뿐 아니라 별도 키워드/공식 탐색으로 관련 공고 풀을 구성한다. 전체 카탈로그의 정답 완전성을 확인하지 못하면 Recall을 ‘판정 풀 기준 Recall’로 표시한다. 미판정은 무관으로 처리하지 않고 커버리지·제외 수를 함께 보고한다.
4. **추천 게이트 제안:** 판정 풀 양성의 후보 Recall@20 ≥ 0.90, 최종 반환 항목 Precision ≥ 0.80, 무결과 오추천 질문 ≤ 10%. 실제 분모·오류 건수 병기. 알려진 필수 지역/업력/대상 불일치 추천은 고정 치명 오류 세트에서 0건이어야 한다.
5. **근거 게이트 제안:** 반환 인용의 존재/공고 일치 100%, 사람이 판정한 원문 뒷받침 비율 ≥ 95%. 근거 없는 신청 가능 확정·필수 제외 조건 반전·다른 기업/공고 정보 혼입은 치명 오류 세트에서 0건. 0건 관찰이 위험 0이라는 뜻은 아니다.
6. **대화 회귀:** 후속 좁히기·일부 조건 교체·전체 초기화·충돌·무결과·정보부족·새 공고 버전 각 시나리오 포함. 기존 발화와 새 발화의 어떤 필드가 유지/변경됐는지 기대값을 고정한다.
7. **근거 난례:** 여러 페이지/청크의 AND·OR·우대·예외, 표/각주, 첨부 미수집, 정정/마감 연장, HTML 지시문 공격, 타 공고 혼입을 포함한다. 참조 인용만 맞고 답변 의미가 틀리면 실패다.
8. **성능·비용:** 같은 스냅샷/모델에서 예열·초회 요청을 분리하고 동시 1/4 요청 조건별로 최소 100건의 성공/실패/429·503/지연·사용량을 기록하는 안을 먼저 합의한다. 초기 p95 목표는 검색 20초·근거 질문 25초 이하로 제안하며 미달 시 단계별 시간을 분해한다. 후속 오류 수정에서 조정한 90초 검색 화면 timeout은 성능 목표가 아니다. 기존 분당 한도를 지키는 간격과 테스트 한도 초과 시나리오를 별도로 설계한다.
9. **실제 사용 검증:** 초기 고객 5명 이상이 탐색 → 근거 확인 → 비교/저장 과제를 수행하는 소규모 관찰을 제안한다. 목표는 적격 후보와 확인할 조건을 스스로 설명 가능한지 확인하는 것. 소규모 성공률을 시장 효과로 일반화하지 않는다.

이 수치는 이번에 달성한 성과가 아니라 **첫 평가 전에 팀이 확정할 출시 후보 기준**이다.
실제 모델 실행 횟수·토큰 예산은 별도 산정/동의 후 사용한다. 미달 시 held-out을 튜닝에 재사용하지 말고 실패를 보존한 뒤 신규 검증 세트를 확보한다.

## 8. 구현 규율과 완료 정의

- Core는 기존 기능 중심 `Controller → Service → (Facade) → Client`, DB는 `Service → Repository → MyBatis → MySQL`을 유지한다.
- AI는 구체 Service/Agent를 우선한다. 아직 두 번째 구현체나 실제 반복이 없다면 범용 provider/registry/graph를 만들지 않는다. OpenAI 장애는 명시적 오류로 반환한다.
- 새 영속성은 다음 Flyway migration을 추가한다. 기존 migration 수정·원본 공고 덮어쓰기·사용자 기록 삭제를 중복 제거 수단으로 사용하지 않는다.
- 외부 수집/모델 호출을 DB transaction에 넣지 않는다. 기존 제공처별 전체 수집 검증·공개 세대·내용 해시 보호를 유지한다.
- 새 파서·인증·알림 서비스·실행 계층을 추가하기 전에 의존성·비용·정보 이동·실패 시 행동을 공유한다. 기능 선택 없이 외부 계정을 만들거나 알림을 발송하지 않는다.
- 모든 항목은 코드·회귀 테스트·API 계약·UI 오류 상태·기획 추적 ID·문서·미지원 범위까지 있어야 완료다.
- Core 변경은 JDK 21 전체 테스트, 영속성/동기화 변경은 MySQL 8.4 Testcontainers, AI 변경은 전체 테스트, Frontend 변경은 test/lint/build를 통과시킨다.
- 운영 준비/모델 품질은 단위 테스트 통과와 별도 승인한다. 외부 베타 이전에는 O01을 생략하지 않는다.

## 9. 착수 전에 팀이 선택할 사항

1. 첫 사용자를 초기 창업기업으로 좁힐지, 중소기업 지원사업 담당자를 우선할지.
2. 남은 기간/가용 인원에 따라 단계 1 데모와 단계 3 제품 완성을 각각 언제 목표로 할지.
3. 사람 검토 담당, 실제 모델 평가 호출 예산, K-Startup·중소벤처24 활용 권한 확보 담당.
4. U01 인증 방식과 저장 필드/보관 정책, U03 외부 알림 채널/비용. 이 선택 전에는 해당 외부 연동을 확정하지 않는다.

선택이 아직 없어도 **현재 버그 회귀 검증, Q01 평가 설계, C01 조건 계약, C02 시나리오 테스트 설계**는 진행할 수 있다.
