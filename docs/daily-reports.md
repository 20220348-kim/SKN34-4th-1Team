# 기업 맞춤 일일 리포트

로그인한 회원이 등록한 기업의 지역·업종과 원하는 지원 내용을 이용해, 현재 검색 가능한 접수 중 공고를 추천합니다.
웹에서 오늘 리포트를 확인하고, 수신 주소 확인과 동의를 마친 계정에는 같은 리포트를 이메일로 보냅니다.

## 이번 구현 범위

- `/app/reports`: 지원 목적 저장, 오늘 리포트 생성·재조회, 수신 주소 확인 요청, 정기 수신 동의·해제.
- 공통 공고 카탈로그와 기존 검색을 재사용합니다. 기업별로 전체 공고를 다시 수집하지 않습니다.
- 추천은 기본 최대 3건입니다. 관련도, 매칭 이유, 신청 기간, 자격 확인 상태와 공식 원문 링크를 표시합니다.
- 기업마당 공고는 기존 HTML 근거 답변으로 신청 조건·주의사항·필요서류를 확인하고 인용을 함께 보존합니다.
- 근거 부족·분석 장애·미지원 제공처를 각각 표시합니다. 원문에 없는 서류나 위험요소를 만들어 채우지 않습니다.
- 리포트에 사용한 기업 조건과 결과를 MySQL에 보존합니다. 타인의 리포트는 조회할 수 없습니다.
- 정기 생성과 리포트 메일 발송은 별도 DB Outbox·RabbitMQ 소비자로 처리합니다. 수동 미리보기·SMTP 내용 계약은 유지합니다.
  [RabbitMQ 적용 범위·흐름·장애 경계](rabbitmq-daily-report-generation.md)에 상세 구현을 정리했습니다.

관련도 점수는 **선정 확률이나 신청 자격 보장이 아닙니다.** 기존 검색 점수를 그대로 사용합니다.
설립 연도만 있는 기업 프로필에서 정확한 설립일을 임의로 만들지 않으며, 업력 등 미확인 조건은 신청 전에 확인해야 합니다.
PDF/HWP 첨부 전체 분석, 뉴스 브리핑, 신규 공고만 추리는 알림, 선정 확률 모델은 이번 범위에 포함하지 않습니다.

## 처음 사용하는 순서

새 코드를 반영해 Core API를 다시 빌드·시작하면 Flyway가 `V12`를 적용합니다. 개발 검증은 별도 테스트 DB에서
수행했으며, 이후 2026-09-09 사용자 요청으로 로컬 Core API에도 재빌드·재시작과 `V12` 적용을 완료했습니다.
다른 개발 환경에서는 각자 새 서버 코드를 반영해야 합니다. 기존 MySQL·Qdrant 데이터를 삭제할 필요는 없습니다.

1. 회원가입·로그인 후 기업 정보를 등록합니다.
2. 사이드바의 맞춤 리포트 화면에서 원하는 지원 내용을 저장합니다. 예: `AI 서비스 실증과 사업화 자금`.
3. 오늘 리포트 생성 버튼을 누릅니다. **실제 AI Service/OpenAI 호출과 비용이 발생할 수 있습니다.**
4. SMTP가 설정돼 있으면 수신 주소 확인 메일을 요청합니다. 로그인한 계정의 이메일로만 보냅니다.
5. 메일의 링크를 열고 확인 버튼을 누릅니다. 링크를 열기만 해서는 인증되지 않습니다.
6. 리포트 화면으로 돌아와 수신에 동의하고 정기 발송을 활성화합니다.

주소 확인은 리포트 수신 전용입니다. 계정 전체의 `emailVerified`나 권한 단계를 변경하지 않습니다.
가입 계정의 미인증 주소 및 개발 시드의 인증 표시를 정기 메일 발송 동의로 간주하지 않습니다.
SMTP 미설정 시에는 메일 요청이 실패하며 발송 완료로 표시하지 않습니다. 웹 미리보기는 별도로 사용할 수 있습니다.

서울 날짜별 계정당 리포트 한 건을 만듭니다. 오늘 생성한 입력·결과는 고정되어 미리보기와 이메일에 재사용됩니다.
이후 변경한 기업 정보·지원 목적은 다음 리포트부터 반영됩니다. 화면의 저장된 조건과 날짜를 확인하세요.
생성이 실패하면 같은 입력으로 한 번만 더 시도할 수 있으며, 재시도에도 AI 비용이 발생할 수 있습니다.
단, 정기 큐 작업이 시작된 뒤 20분 이상 완료 기록이 없는 `UNKNOWN`은 추가 과금을 막기 위해 그날의 재시도를 차단합니다.
웹의 `GENERATING`에는 생성 큐 대기도 포함됩니다. 완성된 리포트는 다음 정기 주기에서 발송 큐로 예약하고,
기존 SMTP Client가 전송합니다. 발송 큐를 끄면 기존 직접 발송을 유지합니다. [발송 큐 상세](rabbitmq-daily-report-delivery.md)를 참고하세요.

## 발송 환경 설정

SMTP 전송에는 Spring Boot Mail을 사용합니다. 특정 유료 발송 업체나 추가 실행 서비스를 강제하지 않습니다.
SMTP 설정 자동 구성과 유한 시간 제한은 [Spring Boot 공식 메일 안내](https://docs.spring.io/spring-boot/reference/io/email.html)를 따릅니다.
루트 `.env.example`을 참고해 비밀정보는 로컬 `.env` 또는 배포 환경의 secret으로 주입하세요.
네이티브 `bootRun`은 `.env`를 자동으로 읽지 않습니다. Compose는 설정값을 Core API에 전달합니다.

| 설정 | 기본값 | 의미 |
|---|---|---|
| `DAILY_REPORT_ENABLED` | `false` | 정기 리포트 스케줄러 활성화 |
| `DAILY_REPORT_QUEUE_ENABLED` | 직접 Core `false`, Compose `true` | 정기 생성 Outbox 발행·소비. 기존 예약 작업은 이 스위치만 켜도 실행 가능 |
| `DAILY_REPORT_DELIVERY_QUEUE_ENABLED` | 직접 Core `false`, Compose `true` | 리포트 발송 Outbox·소비자. 기존 발송 대기는 정기 예약 스위치와 별개로 처리될 수 있음 |
| `DAILY_REPORT_MAIL_ENABLED` | `false` | 확인 메일·리포트 SMTP 전송 활성화 |
| `DAILY_REPORT_FRONTEND_BASE_URL` | `http://127.0.0.1:5173` | 메일 링크의 실제 프런트엔드 origin. 운영은 HTTPS |
| `DAILY_REPORT_FROM` | 빈 값 | SMTP에서 허용·인증한 발신 이메일 주소 |
| `DAILY_REPORT_SEND_HOUR` | `8` | 서울 기준 발송 시작 시간 |
| `DAILY_REPORT_MAX_ACCOUNTS_PER_RUN` | `20` | 스케줄러 한 번의 처리 계정 상한 |
| `DAILY_REPORT_MAX_REPORTS_PER_DAY` | `20` | DB에서 공유하는 일일 리포트 생성 시도 상한. 실패 재시도 포함 |
| `DAILY_REPORT_MAX_PROGRAMS` | `3` | 리포트 추천·근거 확인 최대 건수. 1~3 |
| `SMTP_HOST`, `SMTP_PORT` | 빈 값, `587` | SMTP 서버와 포트 |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | 빈 값 | SMTP 인증 정보 |
| `SMTP_AUTH` | `true` | SMTP 인증 사용 |
| `SMTP_STARTTLS_ENABLED` | `true` | STARTTLS 사용 및 필수화 |
| `SMTP_SSL_ENABLED` | `false` | 연결부터 TLS 사용. 465 방식이면 SMTP 제공자 설정에 맞춰 변경 |

설정 순서는 SMTP·발신자·실제 웹 주소 확인 → `DAILY_REPORT_MAIL_ENABLED=true` → 본인 주소 확인 메일의 수신 검증 →
수신 동의 → 대상·비용 범위를 정한 리포트 발송 검증 → 정기 발송 활성화입니다.
현재 `preview`는 생성·조회만 하며 공개 API에 일회성 리포트 발송 기능은 없습니다. 발송 예약은 스케줄러가
담당하므로 `DAILY_REPORT_ENABLED=true`로 켜면 본인뿐 아니라 조건을 충족하는 다른 계정도 처리될 수 있습니다.
이미 예약된 발송은 이 설정을 꺼도 발송 큐·메일이 켜져 있으면 진행됩니다. 중지 시 세 설정과 SENDING 작업을 함께 확인하세요.
수신 테스트를 위해 전체 스케줄러를 무조건 켜지 않습니다. 서버에서 접근 가능한 공개 웹 origin과 CORS 설정도 일치시켜야 합니다.
설정이 존재한다는 것과 실제 메일 도착 검증은 다릅니다. 이번 자동 테스트에서는 외부 SMTP나 유료 AI를 호출하지 않습니다.
기존 검색과 근거 답변에 필요한 AI Service·OpenAI 키·벡터 색인도 준비돼 있어야 합니다.
정기 실행에는 RabbitMQ와 큐 스위치도 필요합니다. `DAILY_REPORT_ENABLED=true`이면서 큐가 비활성이면 시작을 거부합니다.
업그레이드에는 생성 작업 테이블 V23과 기존 리포트의 발송 Outbox 컬럼 V27이 적용됩니다. 기존 migration은 수정하지 않습니다.

한 번 생성할 때 검색·추천과 최대 3건의 근거 답변 경로를 호출합니다. 캐시·청크 임베딩·하위 재시도에 따라
OpenAI HTTP 호출 수가 달라지므로 생성 상한을 API 호출 횟수 또는 금액 상한으로 해석하면 안 됩니다.
AI 제공자의 사용량 제한·비용 관측은 별도로 설정해야 합니다.

### Gmail로 로컬 발송 준비

현재 구현은 SMTP 계정 인증을 사용하며 Google OAuth 연결 기능은 없습니다. Gmail SMTP는
`smtp.gmail.com`, STARTTLS 포트 `587`로 설정합니다.
[Google 공식 SMTP 안내](https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app?hl=en)

1. 본인 Google 계정의 2단계 인증을 활성화합니다.
2. [앱 비밀번호 관리](https://myaccount.google.com/apppasswords)에서 이 프로젝트용 앱 비밀번호를 만듭니다.
3. Git에서 제외된 루트 `.env`에 아래 값을 설정합니다. 기존 항목이 있으면 중복 추가하지 말고 수정합니다.

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_AUTH=true
SMTP_STARTTLS_ENABLED=true
SMTP_SSL_ENABLED=false
SMTP_USERNAME=본인의_Gmail_주소
SMTP_PASSWORD=발급받은_앱_비밀번호
DAILY_REPORT_FROM=SMTP_USERNAME과_같은_Gmail_주소
DAILY_REPORT_MAIL_ENABLED=false
DAILY_REPORT_ENABLED=false
```

앱 비밀번호는 Google 로그인 비밀번호가 아니며, 입력 시 표시용 공백을 제거합니다.
Google은 지원되는 앱에서는 OAuth 로그인을 권장합니다. 앱 비밀번호 메뉴가 없으면 조직 정책·고급 보호·
2단계 인증 방식 등의 제한을 확인하며, 보안 기능을 끄는 방법으로 우회하지 않습니다.
[Google 공식 앱 비밀번호 안내](https://support.google.com/accounts/answer/185833?hl=ko)

비밀번호는 채팅·로그·스크린샷·Git에 남기지 않습니다. 설정 파일의 값을 출력하는 대신 필수 항목의 설정 여부만
확인합니다. `.env` 수정만으로 실행 중 Docker 컨테이너에 반영되지는 않습니다.
처음에는 메일 전송만 활성화하고 Core API를 재생성하되, 기존 수집·색인 스위치 상태와 정기 발송 비활성 상태를 유지합니다.
확인 메일은 로그인한 GovBiz 계정의 이메일로만 전송되므로 개발용 가상 주소가 아닌 본인이 수신할 수 있는 계정으로 검증합니다.
메일의 `127.0.0.1` 링크는 서버를 실행한 컴퓨터에서 열어야 합니다.
수신 주소 확인 메일은 AI를 호출하지 않지만, 오늘 리포트 생성은 별도의 유료 호출을 발생시킬 수 있습니다.

## API

`/me` 경로는 기존 세션의 `Account`를 사용하며 클라이언트가 소유자 ID나 수신 이메일을 지정하지 않습니다.
개인 응답은 `Cache-Control: no-store`, 쿠키가 붙은 쓰기 요청은 기존 Origin 검사를 적용합니다.

| 메서드·경로 | 동작 |
|---|---|
| `GET /api/v1/me/daily-reports/settings` | 지원 목적·수신 동의·주소 확인·SMTP 설정 여부 |
| `PUT /api/v1/me/daily-reports/settings` | `supportPurpose`(최대 100자), `enabled`, `consent` 저장 |
| `POST /api/v1/me/daily-reports/verify-email` | 본인 주소 확인 메일 요청. 성공 204 |
| `POST /api/v1/daily-reports/email/confirm` | 본문의 `token` 검증·소비. 성공 204 |
| `POST /api/v1/daily-reports/email/unsubscribe` | 본문의 `token`으로 정기 수신 해제. 성공 204 |
| `POST /api/v1/me/daily-reports/preview` | 오늘 리포트 생성 또는 저장본 반환. `{report: ...}` |
| `GET /api/v1/me/daily-reports/latest` | 본인 최신 리포트. 아직 없으면 `{report: null}` |

리포트에는 당시 기업명·지역·업종·지원 목적, 추천·인용, 경고, 생성·발송 상태가 포함됩니다.
설정 응답의 `emailDeliveryAvailable`은 SMTP 설정 여부, `schedulerEnabled`는 자동 발송 스케줄러 활성화 여부입니다.
메일 설정만 있고 스케줄러가 꺼져 있으면 새 정기 예약은 하지 않습니다. 단, 발송 큐가 켜져 있으면 기존 발송 대기는 처리될 수 있습니다.
`GENERATING`, `READY`, `FAILED`로 생성 상태를, `NOT_REQUESTED`, `SENDING`, `SENT`, `UNKNOWN`, `SKIPPED`로 발송 상태를 구분합니다.
정확한 공개 응답 타입은 `dailyreport/controller/dto`와 프런트엔드 `DailyReportDto`에서 함께 검증합니다.

## 장애·중복·보안 경계

- 날짜별 생성 예약과 계정별 최대 2회 생성 시도, 전역 일일 예산을 DB에서 원자적으로 관리합니다.
- 생성 예약은 `READ_COMMITTED`와 구독 행 잠금을 사용합니다. 같은 계정의 중복은 직렬화하고, 서로 다른 계정의 없는 리포트 행에 걸리는 gap lock과 일일 예산 잠금의 교착은 피합니다.
- 수동 생성의 만료 재시도 및 정기 생성의 확인된 실패 재시도에는 새 실행 키를 사용해 이전 실행이 결과를 덮어쓰지 못하게 합니다.
- 정기 작업의 시작 전 대기는 최대 1시간/서울 자정까지이며, 시작 후 20분 이상 결과가 없는 경우 `UNKNOWN`으로 남겨 자동·수동 재시도를 차단합니다.
- 준비 중·검색 장애를 정상적인 추천 0건으로 숨기지 않습니다. 일부 제공처만 준비된 검색에는 경고를 남깁니다.
- 발송 직전에도 활성 계정·확인된 수신 주소·현재 수신 동의를 검사합니다.
