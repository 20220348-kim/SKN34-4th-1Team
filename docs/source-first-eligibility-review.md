# 공식 본문 우선 자격 검토 — 랭킹 v4

[문서 목록](README.md) · [API 계약](support-program-search-contract.md) · [C01 기록](company-conditions-search.md)

기준일: 2026-09-07. C01 기업 조건 검색 구현 이후, 서울 조건에 경북 사업장 이전·확장 확약 문구가 있는
공고가 추천된 사례를 계기로 사용자가 승인한 수정이다. 이 문서는 이번 변경과 검증만 다룬다.

## 관측한 문제

대상은 기업마당 `BIZINFO:PBLN_000000000126064`, 「2026년 제조 특화 온디바이스 AI 기반 자율제조
실증 기반 구축사업 기업지원 프로그램 수혜기업 모집 공고」다.
[공식 상세 페이지](https://www.bizinfo.go.kr/sii/siia/selectSIIA200Detail.do?pblancId=PBLN_000000000126064)의
사업개요에는 지원기간 안에 경상북도로 사업장을 이전하거나 확장하겠다고 확약하는 기업의 신청 가능 문구가 있다.
진단 시 첨부 공고 PDF 1쪽에서도 같은 문구를 확인했다. 이는 이번 수동 진단이지 production의 첨부 판독 기능이 아니다.

로컬 상세 GET에서 이 공고의 `regions`는 `["전국"]`, `targetDescription`은 `중소기업`이었다.
공식 API 본문인 `summary`에는 이전·확장 확약 문구가 이미 있었다. 기존 Mapper는 지역 해시태그가
10개 이상이면 전국으로 합쳤으며, v3는 모델이 붙인 `INCOMPATIBLE`만 제외했다. `UNKNOWN`이나
잘못된 `MATCH`가 높은 점수와 함께 반환되면 일반 추천으로 노출될 수 있었다.

당시 사용자 검색의 실제 요청·모델 원출력은 보존돼 있지 않으므로, 그 실행에서 조건 전달이 빠졌는지
모델이 어떤 자격 라벨을 출력했는지는 확정하지 않는다. 위 내용은 실제 저장 데이터와 코드상 허용 경로의 진단이다.

## 변경 기준

1. 태그는 후보 검색에만 사용하는 보조 정보다. 전국 태그가 원문의 소재지 제한·예외를 덮어쓰지 않는다.
2. 대상·지역별로 `MATCH`, `INCOMPATIBLE`, `UNKNOWN`과 설명·본문 인용을 함께 생성한다.
3. `MATCH`/`INCOMPATIBLE`에는 실제 전달된 `summary` 또는 `targetDescription`의 연속 구절 인용이 필수다.
   AI와 Core가 같은 후보·같은 필드의 정확한 부분 문자열인지 검사한다. 다른 후보·태그·기관명·제목은 근거로 삼지 않는다.
4. 하나라도 `INCOMPATIBLE`이면 점수와 무관하게 제외한다. 하나라도 `UNKNOWN`이면 확인 필요 묶음으로 분리한다.
   두 축 `MATCH` 공고가 우선이고 각 묶음 내부는 기존 총점순이다. 최소 의미 점수 20·총점 60, 합계 최대 5개는 유지한다.
5. 현재 서울 소재라는 사실만으로 경북 이전 계획을 추정하지 않는다. 이전·확장 확약 같은 사용자 정보가
   불명확하면 해당 내용을 확인하도록 설명하고, 일반 조건 확인 공고로 취급하지 않는다.

## 구현 경계

- 내부 계약은 `govbiz-support-program-ranking-v4`. 공식 API 본문 입력은 summary 6,000자,
  targetDescription 2,000자까지 확장하고, 절단되면 `sourceTextTruncated=true`로 두 축 모두 UNKNOWN만 허용한다.
- 인용은 축당 최대 1개·240 Unicode code point, 설명은 160 code point다. 공백뿐인 값과 Unicode C 문자를 거부한다.
  원문 인용을 임의로 다듬거나 재작성하지 않는다.
- 공개 검색 결과의 `eligibilityReview`는 판정·설명·인용과 `basis=OFFICIAL_API_TEXT`를 제공한다.
  검색별 결과일 뿐 DB에 저장하지 않으며 상세 GET·최신 목록에는 사용자별 판정이 없다.
- Frontend는 조건 확인 공고와 확인 필요 공고를 분리하고, 점수보다 자격 확인 상태를 먼저 표시한다.
  이전 응답처럼 판정 없는 점수 공고도 확인된 자격으로 표시하지 않는다.
- 현재 근거는 정기 수집한 공식 API 본문이다. 상세 HTML을 검색마다 새로 수집하지 않으며, 첨부 PDF/HWP
  자동 판독·OCR·수정 공고 간 우선순위 해석은 이번 범위에 포함하지 않는다. 화면에도 첨부 미검증을 알린다.
- 실제 흐름은 `HTTP API → Service → Agent → OpenAI → Response`다. 기존 후보 랭킹 Agent 1회 호출을 유지한다.
  질의 임베딩은 기존 별도 호출이다. 새 provider·Agent 프레임워크·규칙 기반 장애 fallback·production 의존성은 없다.
- 후보별 설명·인용이 늘어나 랭킹 출력 한도를 4,000에서 10,000토큰으로 늘렸다. 실제 출력량만큼 비용이 발생하며,
  당시 모델 25초·전체 실행 30초 제한을 유지했다. 후속 [검색 오류 수정](support-program-ranking-timeout-fix.md)에서
  랭킹 전용 45/50초와 원문 조각 번호 선택·복원을 추가했다. 아래 기록은 최초 원문 우선 구현 당시 결과다.
- 본문과 태그가 충돌할 때 태그를 근거에서 제외하지만, 인용 존재 검증만으로 AI의 논리적 판정 정확성을 보장하지 않는다.
  `MATCH`는 제공된 정보에서 확인한 대상·지역 관계이며 모든 신청 요건·선정 가능성에 대한 보증이 아니다.
  [OpenAI Docs의 Structured Outputs 안내](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)도
  구조화된 출력에 내용 오류가 남을 수 있음을 명시한다. 형식·인용 검증과 의미 정확도 평가를 구분한다.

## 검증 기록

아래는 이번 수정 후 새로 실행한 결과다. C01의 Frontend 208·AI 256·Core 421개를 재사용하지 않았다.
사용자는 이번 수정 검증용 JDK 21 컨테이너의 Docker 소켓 연결을 별도로 승인했다.
테스트용 MySQL 8.4만 생성·정리했으며 기존 개발 서비스·DB를 테스트 대상으로 사용하지 않았다.

| 범위 | 실행 결과 |
|---|---|
| Frontend 전체 | 24개 파일·236개 테스트 통과, `tsc -b`·oxlint·Vite production build 통과 |
| AI Service 전체 | 319개 통과, 21.23초. 실제 조건부 문구를 사용한 조건 입력 유무 회귀 2건 포함 |
| Core API 전체 | JDK 21.0.12+8, `./gradlew clean test --no-daemon --no-watch-fs --project-cache-dir /root/.gradle/core-audit-project`; 44 suites·433개, 실패·오류·건너뜀 0. 실제 MySQL 8.4.11 통합 43개 포함, 7분 13초 |
| 검색 평가 도구 | 검색 평가 디렉터리 최상위 `test_*.py` 62개 통과. Windows 심볼릭 링크 권한 오류 2건은 네트워크 없는 Linux 컨테이너에서 전체 62개 재실행해 통과. `review/`의 별도 과거 판정 테스트를 이번 62개에 포함하지 않음 |
| 브라우저 가상 응답 | 서울 조건 POST 전송, MATCH 75점이 UNKNOWN 95점보다 먼저 표시, 확인 필요만 있는 응답 분리, 설명·인용·첨부 미검증 안내를 확인. 실제 모델 정확도 검증은 아님 |
| 정적 확인 | `git diff --check` 통과. Repository·MyBatis XML·Flyway·production 의존성과 과거 평가 실행 자료는 변경하지 않음 |

검증 항목은 전국 태그와 지역 제한 충돌, 경북 이전·확장 확인 필요, 본문상 전국 대상, 자격 정보 부족,
정확하지 않은 인용·다른 후보 인용·미지원 근거 필드 거부, 절단 표시, 묶음별 정렬, 공개 DTO·UI 연결이다.

실제 공고 문구 회귀는 미리 지정한 모델 응답을 사용해 계약·필터·설명 보존을 검증한다.
프롬프트가 실제 OpenAI 모델에서 항상 같은 의미 판정을 유도한다는 증거로 해석하지 않는다.
별도로 제안한 최대 3회 유료 모델 검증은 승인 답변이 없어 실행하지 않았다. 기존 v3 평가 실행 결과와 공유 자료는 보존한다.

## 로컬 반영 기록

사용자가 검증 후 Core·AI 재빌드·재시작을 승인했고, 위 검증 후 반영했다.
Core는 기존 Compose 빌드, AI는 기존 uv 다운로드 캐시 오류를 피하기 위해 `uv sync --no-cache`만 추가한
임시 Dockerfile로 같은 잠금 의존성과 최종 소스를 빌드했다. 저장소 Dockerfile은 변경하지 않았다.
두 서비스 각각 `up --detach --no-deps --no-build --pull never`로 교체했다.

- 새 Core 컨테이너: `05ea8e826780`, 이미지 `sha256:d7807d11c597bb3a3810198956e5731bb1644f2b39975e60804de1d8a713e6d8`.
- 새 AI 컨테이너: `f477e083059f`, 이미지 `sha256:78e23e34a5b8f12c16d33808f536f0cf22f5cd0c1aa85af570b453533ba067ad`.
- Web `b529a34d6ed1`, MySQL `505a1af7beec`, Qdrant `7c0e50e0ebe7`은 기존 컨테이너를 유지했다.
  `govbiz_mysql-data`·`govbiz_qdrant-data`를 유지했고 초기화·삭제하지 않았다.
- 재시작 후 Core health·Core→AI health가 모두 `up`. AI OpenAPI의 v4·6,000/2,000자 제한·절단 표시와
  실제 조건부 공고 문구가 들어간 최종 프롬프트 반영을 확인했다.
- Web 경유 readiness는 확인 시 `SEARCHABLE`, `indexReady=true`, 공고 1,499개였다. 이것은 준비 상태 기록이며
  실제 모델 검색 성공을 의미하지 않는다. 신고 공고 상세 GET은 정상이고 검색별 자격 검토는 계약대로 null이다.
- 잘못된 검색 POST `{}`는 400으로 거부됐다. 상태·스키마·상세·입력 검증 확인은 모델 호출 없이 수행했다.
- 기존 자동 수집·색인 설정은 유지했다. 재시작 이후 자동 작업은 승인 범위이며, DB 내용 전체가 불변이라고 주장하지 않는다.
- 사용자 요청에 따라 C01 기업 조건 검색과 이번 원문 우선 자격 검토는 한국어 커밋 하나로 관리한다.
  원격 push는 별도 요청 범위다. 브라우저 검증용 임시 서버·탭과 테스트 컨테이너는 종료했다.
