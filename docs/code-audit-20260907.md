# 코드 검수·오류 수정·최적화 기록

[문서 목록](README.md) · [구현 현황](implementation-status.md)

기준일: 2026-09-07. Frontend·Core API·AI Service·평가 도구·Compose의 실행 경로와 참조를 검토하고,
재현 가능한 결함과 확인된 반복 처리만 수정했습니다. 이 기록은 모든 잠재적 버그가 없다는 보증이나
실제 모델의 검색 품질 평가 결과가 아닙니다.

## 보존 및 삭제 범위

- SampleItem, Hook/Redux 비교 화면, 학습용 예제·테스트·문서는 그대로 보존했습니다.
- 소스 파일 삭제는 없습니다. 실제 사용처가 없는 `BizInfoProgramPayload.applicationMethod`와
  해당 디코딩, 상세 화면의 `emptyReason` 스타일 키만 제거했습니다.
- 사용하지 않는 기업마당 필드 `reqstMthPapersCn`의 타입 때문에 공고 목록 전체를 거부하던 문제도
  함께 수정했습니다. 실제 사용하는 필드와 페이지 완전성 검증은 유지합니다.
- 자동 실행되지 않더라도 테스트·명시적 API 계약이 있는 색인 정리 등의 코드는 삭제하지 않았습니다.
- 기존 평가 스냅샷·판정 원표·실행 캡처, Flyway migration, 기존 개발 변경은 보존했습니다.
- 신규 production 의존성·외부 서비스·범용 추상화는 추가하지 않았습니다. 유료 API 호출은 0회입니다.

## 수정 내용

| 영역 | 재현된 문제 | 수정 |
|---|---|---|
| 검색 입력 | NUL·제로폭 문자 등이 AI까지 전달되어 입력 오류를 AI 장애로 처리 | 공개 Controller에서 400 검증. 빈 검색·탭·줄바꿈·정상 이모지는 유지 |
| 색인 장애 | 정기 복구가 `index_ready=false`를 기록하면 기존 최신 목록도 사라지고 자연어 검색도 정상 빈 결과가 될 수 있음 | 빈 검색은 공개된 DB 스냅샷을 유지하고, 전체 색인 불가 시 자연어 검색은 503으로 구분 |
| 제공처 노출 | 빈 검색을 복구하며 미공개 제공처를 잘못 노출할 위험 | 공개 세대·지문을 요구. 초기 빈 DB·정상 0건·부분 준비·미복구 legacy를 MySQL 테스트로 구분 |
| AI 동시 처리 | 큰 공고 배치의 토큰화가 HTTP 이벤트 루프를 막음 | 두 색인 Service에서 반복되던 토큰 상한 처리를 함수 하나로 공유하고 작업 스레드에서 실행 |
| 검색 화면 | 상태 안내가 추가되면 검색·취소 버튼이 입력창 밖으로 겹침 | 입력창과 버튼만 같은 위치 기준 컨테이너에 배치 |
| 상태 조회 | 응답이 오지 않으면 검색 화면이 계속 잠김 | 10초 후 취소·오류 안내·수동 재확인. 늦은 응답과 이탈한 화면의 타이머 정리 |
| 화면 표시 | 준비된 공고 수를 전체 동기화 공고 수처럼 표시 | ‘검색 가능한 공고’로 명확히 표시하고 날짜 formatter 재사용 |
| 평가 저장 | 파일 쓰기 실패로 이전 기록이 잘리거나 API 클라이언트를 닫지 못함 | 임시 파일 완성 후 교체하고 `finally`에서 클라이언트 종료 보장 |
| 평가 중단 | 예상하지 못한 HTTP 500 뒤에도 다음 평가 요청 실행 | 실패 상태 기록 후 원래 오류 유지, 후속 요청은 503으로 거부 |
| Compose 정리 | 기존 프로젝트 이름을 지정하면 설정·시작 실패에도 해당 자원 삭제 가능 | 설정 검증·기존 컨테이너/네트워크/volume 확인을 정리 trap보다 먼저 수행하고 기존 자원이 있으면 중단 |
| 평가 성능 | 질문마다 동일 공고 본문을 다시 토큰화 | 한 실행 안에서 공고별 토큰을 한 번 계산. 실행 간 전역 캐시는 없음 |

빈 검색은 `Controller → Service → Repository.findPublishedPresent → MyBatis → MySQL`이며
공개 이후 색인 장애와 독립적입니다. 자연어 검색·신규 평가는 `findSearchablePresent`로 색인 준비도
요구하고, 일부 제공처만 준비되면 그 제공처만 사용합니다. 상세 조회의 기존 경계는 유지합니다.

AI 점수화·근거 답변의 `HTTP API → Service → Agent → OpenAI → Response` 흐름은 바꾸지 않았습니다.
공고·근거 색인의 공유 전처리만 이벤트 루프 밖으로 이동했으며 모델·프롬프트·토큰 상한·배치·해시·오류
계약은 그대로입니다. 새 Registry, DAO, Agent 프레임워크는 만들지 않았습니다.

최초 통합 검증은 색인 장애 뒤 `{"query":"","programs":[]}`가 되는 회귀를 발견해 실패했습니다.
MySQL 회귀 테스트로도 실패를 재현한 뒤 수정했으며, 스모크도 정기 복구가 장애 상태를 저장한 **이후**
자연어 503·기존 목록 200을 확인하도록 강화했습니다. 최종 실행은 Qdrant 재시작 후 검색 복구,
SampleItem 준비 API, AI Service 중지 시 장애 분리와 재시작 후 복구까지 통과했습니다.
검증용 컨테이너·volume은 실행 스크립트가 정리하며 기존 개발 데이터는 사용하지 않습니다.

## 최적화 측정과 한계

- 고정 공고 1,422개·질문 16개의 오프라인 기준 검색 결과가 변경 전후 완전히 동일했습니다.
  로컬 3회 측정 중앙값은 0.974초 → 0.0879초였습니다. 운영 검색 API 응답속도 측정은 아닙니다.
- 허용 입력 50개 × 12,000자의 임베딩 전처리를 외부 호출 없이 비교했을 때, 단회 측정의 최대
  이벤트 루프 정지는 4.704초 → 0.011초였습니다. 운영 처리량이나 전체 지연 개선율을 뜻하지 않습니다.
- 이미 실행 중인 CPU 작업 스레드는 요청 취소 시 즉시 강제 종료되지 않습니다. 기존 입력 상한은 유지합니다.
- 저장 장치 오류 시 마지막 요청의 최신 기록까지 보장할 수는 없지만 이전 완성 캡처는 보존합니다.
- 테스트는 실제 유료 모델의 답변 정확도, 외부 제공처의 최신 응답, 운영 부하·배포 보안 점검을 대체하지 않습니다.
- 같은 Compose 프로젝트 이름으로 검증을 동시에 실행하지 않습니다. 남겨 둔 검증 자원이 있으면
  새 이름을 사용하거나 대상 확인 후 별도로 정리해야 합니다.
