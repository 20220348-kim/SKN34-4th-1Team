# 모바일 신청문서 작성

웹의 신청 준비 계약과 생성 서비스를 재사용하는 React Native 화면이다. 예시 데이터·자동 제출·새 문서 생성 서버를 추가하지 않는다.

## 화면과 진입

| 경로 | 화면 |
|---|---|
| `/all/preparation` | 작성 중·초안 완료 목록, 작업 상태, 새 신청, 관리 모드에서 개별 삭제 확인 |
| `/all/preparation/new` | 필터 검색·관심 공고함에서 한 건 선택 → 저장 양식 확인·선택, 명시적인 유료 분석 요청 |
| `/all/preparation/{id}` | 질문 한 개씩 답변, 문항 목록, 자동 저장·미정·선택지·저장 충돌 확인 |
| `/all/preparation/{id}/review` | 필수 입력 누락과 저장 답변 검토, 명시적인 유료 초안 생성 접수 |
| `/all/preparation/{id}/documents` | 기존 작업 조회·복구, 서버 단계 표시, 생성 파일·이전 버전·미기입 답변, 초안 다운로드 |
| `/all/preparation/{id}/online` | 구글폼 신청 공고에 한해 저장된 답변 복사·TXT 내보내기, 공식 구글폼 이동 |

전체 메뉴의 기존 하단 탭을 유지한다. 오른쪽 위는 검정색 `새 신청 ＋`, 목록 마지막 카드 아래에도 새 신청 버튼을 둔다.
문서 관리는 카드별 삭제 버튼을 표시하고 문서명·공고명을 확인한 뒤 삭제한다. 진행 중·결과 불명 작업이나 작업 조회 실패 시 삭제를 막는다.
관심함과 공고 상세의 신청문서 행·새 문서 버튼도 같은 네이티브 경로로 연결한다.
문서 결과의 `답변 수정하기`는 검토 화면을 거치지 않고 답변 입력 화면을 연다. 문서 결과의 별도 목록 복귀 버튼은 없으며 헤더의 뒤로가기를 사용한다. 답변 입력 화면에는 공식 공고 원문 버튼을 표시하지 않는다.
구글폼 입력 도우미는 기존 `readProgramDetail`의 shared DTO 변환을 거친 공식 신청 경로가 `GOOGLE_FORMS`인 경우에만 표시한다. 직접 `/online`에 진입해도 같은 경로를 먼저 확인하며 그 외 공고는 온라인 폼 분석·안내 API를 호출하지 않는다. 조회 장애는 명시적인 오류로 표시한다.

공고 선택은 중복 검토의 `CatalogScreen`, `ReviewSavedPrograms`, `ProgramCard`를 사용한다.
기존 비교 선택은 최대 두 건을 유지하고 신청문서에서만 최대 한 건·작성 대상 문구를 전달한다.
필터·관심함 패널을 한 번 연 뒤 숨겨서 보존한다. 상세 조회와 선택은 별도 버튼이며 탭 전환과 양식 확인에서 돌아올 때 입력·선택·스크롤을 유지한다.

## 경계와 호출 흐름

`Expo route → mobile screen/hook → shared ApplicationPreparationUseCase → mobile ApplicationPreparationRepository → Bearer HTTP → 기존 Core Controller/Service`.
반환 DTO는 shared의 Zod 모델로 검증한다. 파일 메타데이터·가용성·매핑 변경 확인 계약은 shared로 모으고 웹도 같은 모델을 사용한다.
생성 파일의 형식 표시와 답변 버전 분류는 shared `ApplicationDocumentFiles`를 웹·앱에서 함께 사용한다. 가장 최근에 생성된 답변 버전의 파일을 먼저 보여 주며, 저장 답변이 더 바뀌었으면 차이를 안내한다. 이전 버전 파일은 접어 두고 버전별로 확인·초안 다운로드할 수 있다.
생성 단계와 실패 분류는 순수 shared 업무 함수이며 웹의 이전 경로는 재수출로 유지한다. 화면·세션·기기 파일 API는 모바일에 둔다.
실제 기입 가능 답변은 shared `isWritableApplicationAnswer`로 판단한다. 빈 답변·미정(UNKNOWN)·자동 기입 불가 문항은 기입 대상에서 제외하며, 웹과 모바일이 같은 함수를 사용한다. 검토·결과 화면의 원본 저장·답변 기입·수동 작성 안내는 shared `applicationDraftMode`로 구분한다.
Core·AI의 양식 발견, 문서 생성 큐, 소유권·revision·형식별 기입 경계는 유지한다. 브라우저 다운로드를 위해 Core의 파일 전용 링크 발급·ticket 다운로드 HTTP 계약을 추가한다.
문서 결과는 서버의 미기입 사유·입력칸 글자 수와 남은 예시 문구 수를 보존하고, 모바일에서도 직접 작성·제출 전 확인 안내를 표시한다.

서버에는 최신 main의 계정별 최근 생성 작업 조회와 `seen` 계약이 필요하다. 서버 이미지가 오래되어 API가 없으면 오류로 표시하며 빈 목록으로 대체하지 않는다.
최근 작업은 GET으로 읽고 QUEUED/RUNNING은 짧은 간격, UNKNOWN은 긴 간격으로 조회한다. 화면 재진입은 기존 작업을 이어받고 유료 POST를 자동 반복하지 않는다.
문서 목록·결과·양식 분석과 관심함 준비 요약의 반복 조회는 화면 이탈 또는 앱 백그라운드 전환 시 중단하고, 전경 복귀 시 기존 상태를 다시 읽는다. 같은 공고의 양식·분야 선택은 복귀 시 유지한다. 다음 준비 요약 조회는 이전 응답이 끝난 뒤 예약하며 조회 실패에는 자동 반복을 중단한다.

## 입력과 실행 보존

답변 작성 하단의 이전·다음 버튼은 한 행에서 같은 너비를 사용한다. 답변 작성·새 문서·중복 검토의 하단 버튼은 탭이 확보한 안전 영역을 다시 더하지 않고 위·아래 8px 여백과 기존 44px 최소 터치 영역을 유지한다. 본문 끝에는 별도 하단 여백을 추가하지 않으며 끝 탄성 스크롤을 차단한다. 결과·목록의 당겨서 새로고침은 유지한다. 키보드 회피는 실제 Stack 헤더 높이를 사용하며 iOS는 하단 여백, Android는 화면 높이를 조정한다. 글자 확대 시 버튼 글씨가 줄바꿈할 수 있도록 높이를 고정하지 않는다.

- 입력 후 2초에 항목 단위로 저장한다. 저장 중 다시 바뀐 답변은 보존하고 다음 요청은 반환된 최신 revision으로 직렬 저장한다.
- 미정은 UNKNOWN 사실로 저장하고, 공백은 해당 답변 제거로 처리한다. 원문 선택지가 있으면 그 선택지만 허용한다.
- 409 충돌 시 최신 서버 답변을 다시 읽고 로컬 입력을 보존한다. 비교 후 내 답변 저장 또는 서버 답변 사용을 사용자가 선택한다.
- 미저장 입력이 있는 화면 이탈은 저장 완료 뒤 진행한다. 저장 실패는 입력을 남기고 이탈을 막는다. 앱 백그라운드 전환 시에도 저장을 시도한다.
  OS 강제 종료·오프라인 상태에서 저장되지 않은 입력의 영속 보존을 보장하지 않는다.
- 유료 분석·생성 전에 requestKey와 대상 식별자/revision만 SecureStore에 계정·API별로 보관한다. 토큰·답변은 이 보관 기록에 넣지 않는다.
- 접수 여부가 불명확하면 보관 요청을 유지한다. 목록·대상 화면에서 같은 requestKey로 확인하며 새 키로 자동 재시도하지 않는다.
- 대상 문서가 삭제되어 같은 요청 확인이 막히면 목록 또는 문서 결과의 `보관 요청 대상 확인`을 사용한다. 인증된 문서 GET이 `404 / APPLICATION_PREPARATION_NOT_FOUND`를 반환한 경우에만 계정·API별 같은 보관 기록을 정리한다. 문서가 남아 있거나 통신·인증 실패·기능 미지원 404이면 기록을 유지한다. 확인 중 요청이 바뀌거나 계정이 전환되면 새 기록을 지우지 않는다. 로그아웃만으로 미확인 유료 요청을 버리지 않는다.
- 필수 답변이 비어 있어도 저장된 답변만 기입해 초안을 만들 수 있다. 전부 비어 있거나 미정이면 AI 호출 없이 공식 원본을 저장한다. 실제 답변이 있지만 자동 기입할 수 있는 답변이 없으면 원본으로 대체하지 않고 서버의 `APPLICATION_DOCUMENT_NO_WRITABLE_INPUT` 오류를 표시한다.
- 생성 전 미저장 답변을 먼저 저장하고 반환된 최신 revision을 사용한다. 저장 실패·충돌, 진행 중·결과 불명 작업은 생성을 막고, 현재 revision 파일이 이미 있으면 재생성 대신 결과로 이동한다. 검토·결과 조회만으로 생성하지 않는다.
- 양식 입력 위치 변경은 승인 토큰·revision을 검증한 API로 적용한다. 기존 답변·파일은 보존하며 적용만으로 유료 생성을 실행하지 않는다.

## 기기 파일

초안 다운로드는 React Native `Linking`으로 시스템 브라우저를 연다. Expo Go와 배포 앱에서 같은 경로를 사용하며 새 네이티브 모듈을 추가하지 않는다. TXT 공유에는 기존 Expo SDK 57의 `expo-file-system`, `expo-sharing`을 사용한다. 화면 이탈 방지는 `expo-router/react-navigation`의 `usePreventRemove`로 Router와 같은 컨텍스트를 사용하며 외부 `@react-navigation/*` 패키지를 추가하지 않는다.
문서 결과는 웹·앱 모두 형식·파일명·용량을 표시한 각 파일 카드에 `초안 다운로드` 하나를 둔다. PDF·HWP·HWPX·DOCX·XLSX를 원래 형식과 파일명 그대로 받는다. 상단·하단의 통합 다운로드, ZIP 묶음 및 문서 결과의 별도 공유 버튼은 제공하지 않는다. 이전 버전 파일도 펼친 뒤 개별 다운로드한다.
앱의 `prepareApplicationDocumentDownload`는 Bearer `POST /api/v1/application-preparations/{id}/documents/{fileId}/download-link`로 본인 파일의 2분 링크를 발급받는다. DTO의 준비 건·파일 ID·정확한 상대 경로·ticket 형식을 검증하고 같은 API origin의 URL만 브라우저에 전달한다. 로그인 JWT는 URL로 보내지 않는다.
브라우저는 해당 파일의 `GET .../download?ticket=...`을 호출한다. Core Service는 기존 Redis의 해시 키 grant·만료와 현재 계정 상태·파일 소유권을 다시 확인하고 원래 MIME·UTF-8 파일명·attachment/no-store/no-referrer로 응답한다. HEAD·재시도를 위해 2분 내 재사용할 수 있으며 만료·삭제·정지된 링크는 410 오류로 처리한다. Redis 장애는 정상 다운로드나 단순 만료로 숨기지 않는다.
앱에서 폴더 선택창을 열지 않으며 저장 위치·중복 파일명·다운로드 확인·취소는 기본 브라우저가 처리한다. 브라우저를 열었다는 안내만 표시하고 파일 저장 성공으로 표현하지 않는다. 링크 발급 실패와 브라우저 실행 실패는 오류로 표시한다. iOS/Android 및 기본 브라우저에 따라 다운로드 확인 화면이나 파일 미리보기가 표시될 수 있다.
구글폼 입력 도우미의 TXT 공유는 기존 OS 공유 화면을 사용하고 화면 종료만 안내하며 파일 전달·저장 성공으로 표현하지 않는다. 로그아웃 시 이번 실행에서 생성한 비공개 임시 파일을 정리한다.
사용자가 브라우저로 저장하거나 다른 앱으로 내보낸 파일은 지우지 않는다. 계정 변경·화면 종료·백그라운드 이후의 늦은 링크 응답으로 브라우저를 열지 않는다.
Stack에서 다른 화면으로 이동해 기존 화면이 남아 있어도 포커스를 잃으면 다운로드·TXT 내보내기를 취소한다. 화면 복귀 후에도 이전 요청의 응답은 사용하지 않으며, 새 요청은 사용자가 다시 선택한다. 이 취소는 서버에서 진행 중인 문서 생성 작업을 중단하지 않는다.
이미 브라우저에 전달한 링크·다운로드는 앱에서 중단하지 못한다. 로그아웃 뒤에도 전달한 파일 전용 링크는 최대 2분 유효할 수 있으며 계정 정지/삭제·문서 삭제는 서버가 다시 확인한다. HWP/HWPX를 읽고 편집할 앱의 설치 여부와 브라우저 저장 동작은 실제 OS에서 확인해야 한다. 공유 화면 취소를 파일 전달 성공으로 표시하지 않는다.

## 개발 PC 확인

PowerShell에서 저장소 루트:

```powershell
pnpm.cmd install --frozen-lockfile
pnpm.cmd --filter @govbiz/mobile start --clear
```

최신 Core 코드(다운로드 링크 API 포함)·기존 Redis·Flyway V47과 AI 문서 서비스를 별도로 반영한다. 다운로드 변경은 migration이나 새 의존성을 추가하지 않는다. `.env`만 수정하거나 기존 이미지를 재시작한 것으로 새 API가 반영됐다고 가정하지 않는다.
Expo Go에서는 휴대폰 브라우저에서 접근할 수 있는 같은 LAN의 개발 API 주소를 사용한다. 배포 앱은 `EXPO_PUBLIC_API_BASE_URL`을 공개 HTTPS origin으로 설정하고 새 Core API를 함께 배포한다. 운영 프록시는 POST의 Bearer와 GET의 ticket 쿼리·attachment 헤더를 전달하고 응답을 캐시하지 않아야 한다. 기존 Vercel middleware의 경로·쿼리·인증 전달을 재사용한다.
실제 문서 분석·생성에는 기존 AI 호출 비용이 발생할 수 있다. 로컬 자동 테스트는 응답·파일 API 테스트 대역으로 유료 호출 없이 검증한다.
시스템 브라우저의 실제 다운로드·TXT 공유와 HWP/HWPX/PDF/DOCX/XLSX 결과 확인은 자동 테스트·JS export와 별개다. Expo Go 및 설치한 배포 앱 양쪽에서 기기 다운로드를 확인해야 한다.
