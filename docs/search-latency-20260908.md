# AI 검색 지연 개선과 실제 비교 — 2026-09-08

이 문서는 당시 일반 처리 배포와 실패를 포함한 실험 기록입니다. 이후 사용자 승인에 따른 Fast 상시
설정과 서울·안산 지역 오류 보완은 [후속 기록](region-conflict-fast-20260908.md)에서 확인합니다.

## 결론

반복 검색의 불필요한 임베딩·랭킹 호출을 줄이고 단계별 지연을 관측하도록 했습니다. 후보 20개,
Sol/low, v5 점수·자격·근거 검증, 모델 45초/Agent 50초 제한은 유지했습니다. 출력 축약은 실제
비교에서 개선되지 않아 서비스에서 제거했습니다. Fast는 효과가 관측됐으나 **기본은 일반 처리**이며,
추가 요금이 발생하는 상시 전환은 별도 선택입니다. 캐시만으로 첫 검색의 시간 초과가 해결된 것은 아닙니다.

## 원인과 채택한 변경

실제 로그에서 조건 해석과 후보 검색은 성공했지만 최종 20개 공고 랭킹이 약 45초에 시간 초과했습니다.
지연의 주된 위치는 OpenAI 랭킹이며, 화면 대기 시간을 늘리거나 후보 수를 줄이는 변경은 하지 않았습니다.

- 랭킹 응답: 서비스 인스턴스별 최대 128개, 성공 검증 후 300초 재사용. 질의·기업 조건·기준일·후보
  내용/메타데이터/순서·결과 제한·버전이 모두 같은 요청만 적중합니다. 입력과 응답은 깊은 복사로 보호합니다.
- 질의 임베딩: 모델·차원·전처리가 고정된 인스턴스에서 정확히 같은 문자열의 검증된 벡터를 최대
  256개/300초 재사용합니다. Qdrant 결과나 공고를 캐시하지 않습니다.
- 동시 요청: 동일 랭킹은 진행 중인 한 작업을 기다립니다. 한 요청 취소는 다른 대기자에게 영향을 주지
  않으며 마지막 대기자가 취소하면 공유 작업을 취소합니다. 임베딩은 질의별 잠금을 사용하고 수행 요청이
  취소되면 남은 요청이 다시 실행합니다. 실패는 저장하지 않고 기존 오류로 전달합니다.
- 최신성: Core의 MySQL 조회·접수 상태 계산, Qdrant collection/현재 ID·해시 전부의 준비 검증과 후보 조회는
  매 검색마다 실행합니다. 공고·조건·날짜가 바뀌면 이전 랭킹을 재사용하지 않습니다.
- CPU·로그: 반복 생성되는 근거 선택 타입은 제한된 LRU로 재사용합니다. `app` INFO에 준비·임베딩·벡터
  검색·모델·검증 시간과 캐시 상태/후보 수를 남깁니다. 키·질문·기업 조건·원문 응답은 기록하지 않습니다.

캐시는 프로세스 메모리에만 있고 재시작하면 사라집니다. 만료는 재사용 차단이며 만료 시점의 즉시 물리 삭제를
보장하지 않습니다. Redis·새 의존성·Agent 프레임워크·fallback·자동 재시도는 추가하지 않았습니다.

실제 흐름은 `HTTP API → Service → Agent → OpenAI → 검증된 Response`입니다. 정확일치 캐시가 있으면
Service에서 검증된 복사 응답을 반환하므로 뒤의 Agent/OpenAI를 생략합니다. 대화의 조건 해석은 별도 단계이며
이 캐시로 생략하지 않습니다.

## 유료 랭킹 비교

같은 공개 공고 20개·질문 5개와 지원금 반복 1개를 단계별 6회 비교했습니다. 매번 새 Service를 생성해
애플리케이션 캐시를 우회했습니다. 재시도 없이 승인된 비교 18회를 실행했으며 실패 5회도 호출 한도에 포함합니다.

| 처리 | 성공/시도 | 성공한 호출의 중앙값 | 시간 초과 |
|---|---:|---:|---:|
| 기존 전체 출력·일반 처리 | 4/6 | 41.097초 | 2 |
| 축약 출력·일반 처리 | 3/6 | 44.775초 | 3 |
| 기존 전체 출력·Fast | 6/6 | 27.165초 | 0 |

동일한 4개 성공 사례끼리 비교하면 **41.097 → 28.617초, 약 30.4% 단축**입니다. Fast 전체 범위는
24.122~31.250초였고, 응답 6개 모두 `priority`로 확인됐습니다. 모든 완료 응답의 입력 캐시 토큰은 0이었습니다.
토큰·실패·필터 전 20개 판정·최종 추천·입력/프롬프트/schema 해시와 재계산 도구를
[평가 기록](../evaluation/support-program-search/runs/search-latency-20260908-v1/README.md)에 보존했습니다.

축약은 내부 ID·필드명·공백을 줄이는 실험이었지만 호출 시간과 실패가 개선되지 않아 미채택했습니다.
기존 출력 계약과 지침은 그대로 두며 실험 코드/테스트는 평가 폴더에만 보관합니다. 단순히 출력 토큰이
줄었다는 이유로 속도가 개선됐다고 판단하지 않습니다. [OpenAI 지연 최적화 안내](https://developers.openai.com/api/docs/guides/latency-optimization)

### 품질 확인과 한계

기존 AI_DRAFT 라벨이 있는 공통 3개 성공 사례에서 일반/Fast 최종 ID와 순서는 같았습니다.
넓은 사업화 질문에서는 기존 일반 응답의 안산 소재지 충돌 공고 1개가 Fast에서 제외됐습니다. Fast의
지원금 반복 2회는 모두 알려진 관련 공고인 모두의 창업 1개를 반환했습니다. 후보 20개 전체와 정확한 인용,
최종 필터·정렬·점수 계산을 별도로 재검증했습니다.

그러나 회사의 서울 소재지와 대구 여성의 개인 조건을 혼동해 공고를 제외하는 기존 누락, 제주 개인 신청
대안을 충분히 반영하지 않는 문제는 남았습니다. 모델의 세부 점수·설명·자격 판정도 호출마다 달라집니다.
사람 정답이 아닌 AI_DRAFT 개발 진단이며, 후보를 고정했으므로 전체 카탈로그 Recall/MRR이 아닙니다.
단계당 6회·순차 실행은 운영 p95나 품질 무저하의 통계적 증명이 아닙니다. 실패를 빈 추천이나 품질 0점으로
취급하지 않았고, 응답 없는 5회의 실제 사용 토큰·비용은 알 수 없습니다.

## 설정과 비용

`OPENAI_RANKING_SERVICE_TIER=default`가 기본입니다. 명시적으로 `priority`를 설정하면 랭킹에만 Fast를
요청합니다. 대화·RAG·임베딩 등급은 바꾸지 않습니다. Sol Fast 토큰 단가는 일반 처리의 2배이며, 실패 시
다른 등급으로 자동 재시도하지 않습니다. 유료 비교 승인과 상시 Fast 활성화는 구별합니다.
[OpenAI Fast 안내](https://developers.openai.com/api/docs/guides/fast-mode)

## 실제 검색 확인

일반 처리 설정으로 서울 SW 기업의 사업화 지원금 검색을 연속 2회 실행했습니다. HTTP는 둘 다 200이며
**42.467초 → 0.484초**, 응답 전체가 같았습니다. 첫 요청의 의미 검색은 3.878초(임베딩 3.645초), 랭킹은
37.236초였습니다. 두 번째는 임베딩/랭킹 캐시 모두 hit였고, Qdrant 재검증·조회 0.144초와 랭킹 0.8ms를
관측했습니다. 이 수치는 확인 검색 API 왕복이며 이전 단계인 대화 조건 해석 시간은 포함하지 않습니다.

**의미 품질 검사는 실패했습니다.** 관련 공고인 모두의 창업은 유지했지만 서울 소재 기업에 안산 한정 공고
`BIZINFO:PBLN_000000000125900`을 UNKNOWN으로 포함했습니다. 같은 종류의 오류가 변경 전 baseline BROAD에도
있었습니다. 캐시는 최초의 검증된 구조를 그대로 재사용하므로 이 의미 오류도 동일하게 반환했습니다.
`run-search.py`는 이 사실을 숨기지 않고 종료 코드 2를 반환합니다. 캐시 적중·HTTP 성공을 품질 통과로
취급하지 않으며, 다음 품질 작업은 회사 소재지와 원문의 지역 제한을 대조하는 판정 오류를 별도로 다뤄야 합니다.

실제 검색은 임베딩 1회·랭킹 1회만 발생해 이번 유료 호출은 **20/22회**로 종료했습니다. Fast 6회는 비교에만
사용했으며 로컬 실행은 `default`입니다. 상시 Fast 전환은 추가 요금에 대한 선택이 필요합니다.
