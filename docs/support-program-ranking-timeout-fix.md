# 지원사업 검색의 랭킹 시간 초과·인용 오류 수정

기준일: 2026-09-07. C02 이후 `서울 AI 창업지원 사업 찾아줘` 검색 실패에 대한 후속 수정이다.

## 관측한 장애와 원인 범위

- 사용자 화면: `지원사업을 검색하지 못했습니다. 잠시 후 다시 시도해 주세요.`
- 당시 Core·AI Health 및 검색 준비 상태는 정상이며 공개 공고 1,550건의 색인 준비를 확인했다.
- AI 접근 로그에서 조건 해석과 후보 검색은 200이지만 랭킹은 두 차례 503이었다.
  후보 검색 완료부터 각각 약 25.279초·25.073초 후 실패했다.
- 실행 설정은 모델 25초·Agent 30초였다. 시간 초과가 유력하지만 기존 로그가 원인 예외를 남기지
  않았으므로 과거 두 요청의 예외 종류를 확정하지 않는다.
- 기존 공용 설정 파서는 30초보다 큰 값을 기본값으로 되돌렸다. 따라서 환경변수로 제한을 늘려도
  의도한 값이 적용되지 않을 수 있었다.
  또한 timeout과 모델/출력 검증 실패를 모두 503으로 합쳐 화면에서 구분하지 못했다.

## 변경 정책

| 경계 | 기존 | 수정 후 |
|---|---:|---:|
| 랭킹 OpenAI 요청 | 25초 | 45초, 요청별 SDK 제한에도 적용 |
| 랭킹 Agent 전체 실행 | 30초 | 50초 |
| Core 랭킹 전용 HTTP 읽기 | 공유 35초 | 전용 55초 |
| Web 확인 검색 | 70초 | 90초 |
| 조건 해석·근거 답변 모델/Agent/Core | 25/30/35초 | 유지 |
| 의미 검색 Core 읽기 | 30초 | 유지 |

새 환경변수는 `LLM_RANKING_MODEL_TIMEOUT_SECONDS`, `LLM_RANKING_RUN_TIMEOUT_SECONDS`,
`AI_RANKING_READ_TIMEOUT`이다. 랭킹 AI 설정은 유한한 양수·60초 이하 및 모델 < Agent 관계를 검사하고,
잘못된 값을 조용히 다른 값으로 대체하지 않는다. 사용자 설정을 바꾸면 상위 Core/화면 제한도 함께
검토해야 한다. 서비스 간 사용자 설정의 관계를 자동 조정하지는 않는다.

랭킹 시간 초과는 내부 504 → Core `504 AI_SERVICE_TIMEOUT` → 화면의 명시적 시간 초과 안내로
전달한다. 다른 모델/출력 검증 오류는 기존 오류로 유지한다. 진단 로그에는 소요 시간·후보 수·안전한
오류 종류만 기록하며 사용자 조건·프롬프트·원문 응답·키는 기록하지 않는다.

후보 수, 모델, HTTP 입출력 계약, 대상/지역의 원문 인용 및 자격 검증은 유지한다.
규칙 기반 fallback·자동 재시도·추가 유료 API 호출도 도입하지 않는다. 확인 검색 실패 후 수동 재시도는
기존 확정 조건을 그대로 사용하며 조건 해석을 반복하지 않는다.

요청 흐름: **HTTP API → Service → Agent → OpenAI → Response**.
Core의 후보 검색 이후 AI 랭킹에서 한 번의 모델 실행과 기존 원문 검증을 수행하고 결과 또는 명시적 오류를 반환한다.

시간 상한 증가는 응답속도 개선이나 품질 합격을 뜻하지 않는다. OpenAI도 timeout을 다른 API 오류와
구분하며, 출력 토큰 생성이 지연의 주요 요소라고 설명한다. 이번 수정은 자격 검증 범위를 축소하지 않고
요청별 시간 예산과 오류 관측을 바로잡는 범위다.
([오류 코드](https://developers.openai.com/api/docs/guides/error-codes),
[지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization))

## 실제 검색에서 추가 확인한 인용 오류

시간 예산 수정 후 Core·AI를 로컬에 반영했다. Web 프록시를 통한 Core/AI Health는 200이고
공고 1,550건의 검색 준비 상태도 정상이었다. 실제 검증 요청은 아래와 같다.

```json
{"query":"서울 AI 창업지원 사업 찾아줘","acceptingOnly":true,"companyConditions":{"region":"서울"}}
```

| 실행 시작(UTC) | 전체 검색 | 랭킹 | 관측 결과 |
|---|---|---|---|
| 2026-09-07 10:18:24.629 | 42.580초 / 503 | 38.451초 / 후보 20개 | 시간 초과가 아닌 `AgentExecutionError` |
| 2026-09-07 10:26:40.256 | 30.162초 / 503 | 28.514초 / 후보 20개 | 안전한 원인 코드 `EXACT_QUOTE_MISMATCH` 확인 |

첫 실제 검증 뒤 원인을 좁히기 위해 5개 검증 실패 지점에 고정 Enum `reason_code`를 추가했다.
이 진단 보강은 AI 전체 **508개 통과**(27.36초) 후 AI만 재빌드·재시작해 적용했다.
메시지·원문·조건·키를 로그에 남기지 않고, 임의 문자열 코드는 허용하지 않는다.
DB 읽기 전용 통계에서 공개 공고 전체의 summary 최대 706자·targetDescription 최대 5자,
입력 한도를 넘어 잘릴 공고 0건을 확인해 본문 절단 가능성도 배제했다.

따라서 시간 제한만 바꾼 상태를 해결 완료로 취급하지 않는다. 실제 두 번째 요청에서는 모델이 생성한
인용문과 해당 필드의 원문 불일치가 확정됐다. 사용자에게 추가 3회 호출 승인을 받았으며,
그중 첫 호출을 원인 확인에, 나머지 2회를 인용 생성 방식 수정 후 검증에 사용했다.
처음 실패를 포함해 이번 실제 검색은 총 4회이며, 추가 승인 3회를 모두 사용한 뒤 더 호출하지 않았다.

## 원문 인용 번호 선택과 복원

Agent는 각 후보의 전달된 `summary`·`targetDescription`에서 변형 없는 240자 이하 조각을 만들고,
후보별 `evidenceOptions`에 짧은 번호·필드·문구를 함께 제공한다. 전체 본문도 그대로 제공하므로
신청 요건과 뒤쪽 예외를 조각만으로 판단하지 않는다. 긴 본문은 겹치는 구간으로 끝까지 순회하며,
제어문자는 문자열을 제거해 이어 붙이지 않고 경계로 나눠 모든 조각이 원문의 연속 구절이 되게 한다.

LLM은 각 대상/지역 판정의 `evidence`에 해당 후보의 번호만 선택한다. Agent가 번호와 후보별 범위를
검증한 뒤 원래 `{field, quote}`로 복원한다. 다른 후보의 같은 번호가 같은 문구를 가리킨다고 가정하지 않는다.
복원 후 기존 Service가 제외·저점 후보를 포함한 전체 20개 후보의 인용·자격·점수를 검증한다.
번호가 잘못됐거나 검증에 실패하면 명시적 오류이며, 정상 결과로 바꾸는 fallback은 없다.

바뀌는 것은 Agent ↔ OpenAI의 내부 선택 형식이다. Core ↔ AI의 v4 HTTP 계약 및 공개 검색 응답은
기존 `{field, quote}` 그대로이며, 모델·배점·최종 추천 기준·후보 수는 유지한다.
이 방식은 원문 복사 오류를 막는 것이며 선택한 근거가 판정을 의미적으로 뒷받침하는지까지 보증하지 않는다.

공식 API 요약을 넘어 첨부문서 전체의 신청 자격을 검증하는 변경은 아니다. 제어문자로 잘게 나뉜 극단적인
본문은 선택지 개수와 입력 크기가 커질 수 있다. 원문을 임의로 누락하거나 자격을 바꾸는 상한/fallback은
추가하지 않았으며, 해당 극단 입력의 비용·지연은 이번 실제 카탈로그 검증으로 입증하지 않는다.

### 자격 의미 정확도의 미해결 한계

두 성공 응답에서 서초구 소재 공고 `BIZINFO:PBLN_000000000125560`의 지역 판정이 `MATCH`였다.
입력은 서울뿐이므로 서초구 소재 여부는 확인되지 않았으며, 해당 판정은 `UNKNOWN`이어야 한다.
`BIZINFO:PBLN_000000000123596`도 지역 인용에 서울 포함 근거가 드러나지 않는데 `MATCH`였다.
원문에 없는 인용 생성은 막았지만 **인용의 존재/문자 일치가 자격 판정의 의미 정확성을 보증하지 않는다**.
따라서 이번 결과를 기업 조건 정확도, 지역 자격 판정 또는 전체 추천 품질 게이트 합격으로 취급하지 않는다.
행정구역 상·하위 범위와 인용의 판정 뒷받침 여부는 별도 후속 개선/실측이 필요하다.
