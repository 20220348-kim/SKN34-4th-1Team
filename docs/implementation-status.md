## Elasticsearch Nori·BM25 후속 반영 (2026-09-12)

단순 키워드 매칭을 Elasticsearch Nori·BM25로 교체했습니다. 현재 MySQL 공고 버전에 한정한 키워드 후보
최대 20개와 Qdrant 의미 후보 최대 20개를 RRF로 결합하고, 기존 AI 점수화에는 최대 20개를 전달합니다.
MySQL 원본·필터 목록·상세·대화 저장·원문 근거 검색은 이 변경으로 대체하지 않았습니다.

공개 전 준비와 정기 복구는 Elasticsearch → Qdrant 순서이며 두 색인이 모두 준비돼야 해당 제공처가
검색 가능합니다. `V24`는 이전 준비 플래그만 재설정하고 공고·대화 기록은 삭제하지 않습니다.
ES 장애는 503으로 반환하며, 기존 MySQL 공고는 유지합니다. 이전 ES 버전 자동 정리는 미구현입니다.

코드 검증은 Core 1,233건·Frontend 1,044건·인프라 25건과 격리 Compose 연결·장애·복구까지 완료했습니다.
이는 실제 MySQL·ES/Nori·Qdrant와 로컬 OpenAI 스텁 기반 검증이며, 유료 실데이터 검색 평가는 아닙니다.
16개 목표 공고 × 3개 질문 형태의 [48개 한국어 진단](../evaluation/support-program-search/runs/elasticsearch-korean-queries-20260912-v1/README.md)도
보존합니다. AI 작성 진단의 목표 공고 포함률을 사람이 검증한 정답 기반 Recall이나 최종 추천 정확도로 해석하지 않습니다.

**구현 검증 종료 시점의 기존 개발 Docker·DB에는 미배포입니다.** 다음 작업은 기존 설정·대기 작업·백업 확인 →
누락 서비스 준비 → Core·AI 재빌드·V24 적용 → 두 색인 복구 → 제공처별 준비 상태 확인입니다.
복구 중 Qdrant 누락 버전의 임베딩 비용은 발생할 수 있습니다. 실제 하이브리드 품질·응답시간 전후 측정은 별도입니다.
[실행 절차](../infrastructure/README.md#백엔드-변경-반영과-화면api-버전-불일치)와
[구조·설정·오류·검증·한계](elasticsearch-lexical-search.md)를 참고하세요.

## RabbitMQ 정기 리포트 생성 후속 반영 (2026-09-12)

정기 일일 리포트 **생성**에 MySQL Outbox와 RabbitMQ를 적용했습니다. 리포트·일일 예산·작업을 함께 예약하고,
Core 내부 소비자 1개가 기존 검색·근거 답변을 재사용합니다. DB 조건부 선점으로 중복 메시지를 처리하며,
실행 후 완료 기록이 없는 작업은 `UNKNOWN`으로 남겨 추가 재시도를 차단합니다.

코드와 격리 검증은 완료했습니다. Core 전체 1,222건·인프라 24건, 실제 MySQL·RabbitMQ 테스트와 Docker의
브로커 중단/재생성 후 복구를 확인했습니다. **2026-09-12 작업 종료 시점의 기존 개발 Docker·실제 DB에는 아직 반영하지 않았습니다.**
유료 API·실제 SMTP 발송·부하 성능 검증도 이번 범위가 아닙니다.

다음 적용 작업은 기존 자동 작업 스위치와 대기 작업을 확인하고 브로커 추가·백엔드 재빌드·Flyway 적용·큐 연결을
확인하는 것입니다. 웹 수동 미리보기·실시간 검색·SMTP 경로, 별도 Worker 서버·운영 고가용성·운영자 복구 도구는
이번에 변경하거나 추가하지 않았습니다. [코드 위치·설정·장애 대응·검증 결과](rabbitmq-daily-report-generation.md)를 참고하세요.

## RabbitMQ 중복 지원·수혜 검토 분석 후속 반영 (2026-09-12)

중복 지원·수혜 검토 분석을 동기 HTTP 처리에서 **202 접수 → RabbitMQ → Core 내부 검토 소비자 → DB 결과 조회**로
전환했습니다. `V25`의 실행 행 자체를 Outbox로 사용해 입력 스냅샷과 발행 대기를 함께 저장하며, 기존 리포트와
다른 큐·소비자를 사용합니다. 새 Worker 서버나 추가 production 의존성은 없습니다.

화면은 대기/분석 중 실행을 자동 조회하고 새로고침·재로그인 후 이력에서 이어 봅니다. 동일 요청·중복 메시지는
새 분석을 만들지 않으며, AI 호출 이후 완료 여부를 모르면 `UNKNOWN`으로 보존하고 자동 재실행과 같은 검토의
새 실행을 차단합니다. 계정별 활성 작업 3건과 기존 공유 동시 실행 한도를 적용합니다.

최종 코드 검증은 JDK 21·실제 MySQL 8.4/RabbitMQ를 포함한 Core 전체 **1,247건**, Frontend 전체 **1,051건**,
인프라 스크립트 **25건**이 통과했습니다. Core는 클린 빌드, Frontend는 lint·production build도 완료했습니다.
격리 Compose에서도 두 quorum 큐/DLQ·소비자 연결과 브로커 재생성 후 재연결, 기존 서비스의 장애/복구를 확인했습니다.
기존 개발 Docker·실제 DB의 새 버전 배포와 유료 실데이터 분석은 별도입니다. 실행하려면 RabbitMQ 연결과
`COMBINATION_REVIEW_QUEUE_ENABLED`, 기존 대기/실행 작업을 먼저 확인해야 합니다.
설정·상태·중복 방지·장애 대응과 검증 결과는 [상세 문서](rabbitmq-combination-review.md)를 참고하세요.

세대 관리는 결과 공개 순서를 보호합니다. 여러 서버가 같은 데이터를 동시에 수집·임베딩하는 작업 자체를
막지는 않습니다. 수집·색인에 실패하면 새 데이터 공개가 지연되며, 첫 동기화가 완료되기 전에는 저장된
공고가 없어 검색 결과가 비어 있을 수 있습니다. Frontend 원문 URL 검증은 제공처 코드별 공식 호스트
허용 목록을 사용하며 기업마당과 K-Startup 공식 도메인 및 하위 도메인만 허용합니다. 위조 URL·알 수 없는
제공처가 섞이면 전체 응답을 거부합니다. K-Startup 수집·정규화·동기화는 구현했으며 데이터의 독립적인 추가 가치와
검색 품질 비교는 별도 검증이 필요합니다. K-Startup 원문 질문은 여전히 미지원입니다.

매 검색마다 Core는 현재 MySQL 공고·접수 상태와 Elasticsearch의 허용 버전 가시성·후보를 확인하고,
AI는 Qdrant collection·전체 현재 버전·후보 조회를
검증합니다. 캐시는 모델·후보 수·배점·시간 상한을 바꾸지 않고 검증된 성공 값만 복사해서 재사용합니다.
TTL은 성공 후 재사용 기한이며 만료 즉시 물리 삭제를 보장하지 않습니다. 같은 입력의 동시 요청은 합류하고,
랭킹은 마지막 대기자의 취소 때 공유 작업을 종료합니다. 임베딩 수행 취소 시 남은 요청이 다시 실행하며
실패를 저장하거나 정상 결과로 보정하지 않습니다. 출력 축약은 미채택이며 기존 출력 계약을 유지합니다.
`OPENAI_RANKING_SERVICE_TIER` 미설정 시 코드·Compose 기본값은 `default`입니다. 제공 `.env.example`은
사용자 승인에 따라 `priority`(Fast)를 명시하며, 현재 Sol의 랭킹 토큰 단가는 일반 처리의 2배입니다.
대화 해석·RAG 답변·임베딩 설정은 바꾸지 않습니다. [검색 지연 개선 기록](search-latency-20260908.md)은
당시 일반 처리 배포·비교 결과로 보존합니다. 후속 지역 지침·schema는 회사·특정 사업장·개인 중 제한 주체를
먼저 구분하고 해당 주체의 주소가 미확인이면 UNKNOWN을 유지합니다. 같은 주체끼리 비교할 때는 서울·서초구의
하위 주소 미확인과 별도 허용 경로 없는 서울·안산의 지역 충돌을 구분합니다. 실제 허용된 이전·별도 사업장 대안은
각각 확인하고, 회사 주소만으로 다른 사업장의 부재나 개인 거주지를 확정하지 않습니다.
현재 Fast 설정·배포·추가 검증 상태는 [지역 충돌·Fast 기록](region-conflict-fast-20260908.md)을 참고하세요.

점수와 `MATCH` 판정은 모델의 판단이며 실제 신청 가능 여부나 선정 확률을 보장하지 않습니다.
코드는 응답 형식·숫자·제외 규칙을 검증하지만, 추천 이유가 원문에 의해 모두 뒷받침되는지까지
독립적으로 검증하지는 않습니다. 접수 상태 또한 파싱된 날짜와 알려진 문구 규칙을 따르며 신청 기간 밖의
모든 예외 조건을 반영하지 않습니다.

| 6단계 API 없는 다중 제공처 준비 | Frontend 전체 162개·lint·build, Core API JDK 21 최종 clean test 363개(MySQL 8.4 통합 포함), 원문 근거 평가 도구 118개·검색 평가 도구 167개와 subtest 167개 통과 | 제공처별 상태·검색·실패 격리·공식 URL·RAG 입력 차단의 회귀 검증. 유료 API 0회, 실제 K-Startup 연동·품질 비교 미실행 |

평가 도구는 후보 단계의 `macroRecallAtK`·무결과 오추천율과 최종 단계의 `macroRecallAt5`·`MRR@5`·무결과
오추천율을 분리해 계산합니다. `evaluation-fixture-export`는 현재 MySQL 카탈로그에서 미라벨 fixture 초안을
만들고, `evaluation-capture`는 실제 Search Service를 다시 구현하지 않고 같은 기준 날짜의 호출 흐름에서 나온
후보·최종 ID를 기록합니다. 실제 snapshot·capture는 `evaluation/support-program-search/runs/`에 보관합니다.
신규 fixture와 capture는 모두 색인 준비된 제공처만 조회합니다. 기존 고정 스냅샷·판정·캡처는 당시 조건의
원본으로 유지하며 이번 상태 필터로 과거 평가 결과를 다시 해석하지 않습니다.
현재 고정 스냅샷·AI 판정·모드 선택 결과는 Git 포함 대상이고 새 실행·임시 출력은 기본적으로 제외합니다.
[공유 자료 검증과 이어받기](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/README.md)를 따릅니다.
선택한 판정 출처와 실제 캡처 없이 검색 품질 점수를 주장하지 않으며, 의미 검색 결과
파일이나 캡처 파일을 제공하지 않으면 각각 출력의 `semantic`·`capture`는 `null`입니다.
[평가 자료와 실행법](../evaluation/support-program-search/README.md)을 참고하세요.

메인 README에서 분리한 단계별 평가 결과는 원본 실행 폴더에서 이어서 확인합니다.

- [3단계 기준선 보고서](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/review-final-v1/report.md): 판정 출처·표본 한계·후보/최종 지표
- [4단계 1차 후보 검색 비교](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/stage4-v1/README.md): 동일 질문의 RRF 결합 전후·제한시간 정렬
- [4단계 2차 고정 후보 랭킹 비교](../evaluation/support-program-search/runs/support-program-catalog-20260906-v1/stage4-v2/README.md): 지원 목적 판단 전후·응답 지연·토큰 사용량
- [4단계 요청 제한·최종 통합 검증](support-program-request-limits.md#4단계-최종-통합-검증-2026-09-06): 제한 구현과 전체 Compose 통과 기록
- [5단계 HTML RAG 후속 검증](../evaluation/support-program-evidence/runs/official-flow-20260907-v1/README.md): 인용 ID 오류 수정·공식 공고 전체 경로·AI-only 정성 검토·API 없는 기록 재검사

저장소를 받은 개발자는 공유 자료 안내의 `verify-shared-run.py --with-capture` 명령으로 API 키·DB·Excel 없이
3단계 원표부터 지표까지 다시 확인할 수 있습니다. 4단계 전후 비교의 재계산 명령은 각 보고서에 있습니다.

현재 Health API는 서비스 응답과 Core→AI 연결을 확인합니다. 검색 화면의 `GET /api/v1/support-programs/readiness`는
마지막 전체 색인 준비 결과와 동기화 이력을 보여 주지만, MySQL·Elasticsearch·Qdrant·OpenAI의 실시간 Health를 한 번에
확인하는 endpoint는 아닙니다. CI 정의가 있다는 사실만으로 특정 원격 실행의 성공을 뜻하지는 않습니다.
실행 명령은 [서비스별 안내](technical-readme.md#상세-문서)와 [CI 정의](../.github/workflows/ci.yml)에 있습니다.

## 현재 제약과 다음 작업

2026-09-12의 우선 적용 작업은 위 Elasticsearch·RabbitMQ 후속 반영 절차입니다. 아래 개발 우선순위는
2026-09-08 계획의 기록이며 이후 기능·배포 상태와 대조해야 합니다. 이번 문서 정리는 전체 개발 계획 재검수가 아닙니다.

| 우선순위 | 작업 | 완료를 판단할 기준 |
|---|---|---|
| 1 | K-Startup 실데이터 반영·추가 가치 평가 | 수집 범위·임베딩 비용 확인 후 활성화하고, 제공처 간 중복·추가 공고·추천 품질을 독립 표본으로 비교. 연동 코드와 전용 필터 구현은 완료 |
| 2 | 외부 공개 전 운영 검증 | 배포 경계와 신뢰할 프록시·서버 수를 확정하고 실제 동시 부하·제한값·상시 지연/실패/사용량 관측을 검증. 현재 요청 제한과 평가 실행 로그를 운영 검증 완료로 취급하지 않음 |
| 3 | 추가 검색·답변 품질 개선 | 새로 관측되는 후보 누락·오추천·답변 누락·지연을 dev 근거와 같은 조건으로 전후 측정. H01 단회 개선을 일반화하지 않고 기존 자료·미확정 질문을 보존하며 이미 노출된 heldout에 맞춰 튜닝하지 않음 |
| 4 | 사용자 기능 확장 | 로그인·세션 위에 회원가입·이메일 인증·기업 등록·영구 기업 프로필·북마크의 제품 범위를 정한 뒤 API·저장·화면까지 연결. C01의 익명 조건 입력과는 별도 범위 |

검색은 현재 MySQL에서 색인 준비된 제공처의 공개 공고만 읽습니다. 비어 있지 않은 검색어를 처리할 때는 접수 상태
필터를 통과한 공고의 제공처 포함 ID와 문서 해시를 내부 API에 보냅니다.
검색·색인 경계의 공고 수 제한은 20,000개이며, 그 이상의 카탈로그나 동시 사용자 부하는 검증된 범위가 아닙니다.
오래된 벡터·Elasticsearch 문서 버전의 저장 공간 정리도 아직 자동화하지 않았습니다. 규모 확장 전에 조회 비용과 색인 수명주기를
측정·개선해야 합니다.

현재 Compose는 개발 환경이며 이메일 인증, 운영 접근 제어, 배포 자동화, 백업·복구 절차는 별도 구현·검증이
필요합니다. 로그인·세션은 동작하지만 Compose는 개발용 시드 로그인을 켜고 쿠키 `Secure`를 끈 상태입니다. 문서 기반 RAG는 기업마당 공식 HTML 한 종류의 공고별 명시적 질문에만 구현되어 있으며,
대화 이력 저장이나 첨부파일 기반 RAG가 구현된 것은 아닙니다.
