# 요금제 사용량 한도

결제 연동 없이 요금제·한도·사용량 기록·화면 표시를 먼저 만드는 작업을 여러 단계로 나눈다. 이 문서는 요금제 기본 구조
(요금제 종류·배정·현재 요금제 조회), 하루 한도(AI 대화 검색·공고 원문 질문), 월 한도(신청 문서 초안·중복 검토), 유료 요금제의
30일 이용권 기간과 기간 총량 한도를 다룬다. 기준 설계는 2026-10-07 「요금제별 사용량 한도 설계」와 2026-10-09 「요금제 설계」이고,
결정마다 웹 조사 결과와 기존 설계 중 하나를 골랐다(섞지 않음). 모든 회원은 FREE에서 시작하며 결제·구독은 아직 받지 않는다.
결제 1단계는 자동갱신 없는 30일 이용권, 그다음은 월 자동결제다. 지금은 운영자가 이용권을 SQL로 배정하고,
회원은 출시 전 무료 체험(플러스·프리미엄 각 14일)으로 유료 한도를 직접 써 볼 수 있다.

## 요금제

| 요금제 | 코드 | 배정 |
|---|---|---|
| 무료 | `FREE` | 모든 회원의 기본값. `account_plan`에 행이 없으면 FREE다 |
| 플러스 | `PLUS` | 30일 이용권. 결제 전이라 운영자가 `account_plan`에 배정한 계정과 14일 무료 체험 중인 계정만 |
| 프리미엄 | `PREMIUM` | 30일 이용권. 결제 전이라 운영자가 `account_plan`에 배정한 계정과 14일 무료 체험 중인 계정만 |

유료 배정은 `assigned_at`(이용권이 시작한 서울 시각)부터 `ends_at`까지 쓰고, `ends_at`이 지나면 행이 남아 있어도 FREE로 센다(V59).
`ends_at`이 없는 배정(운영자·검증 계정)은 `assigned_at`부터 30일마다 새 이용 기간이 시작된다. 시작 전인 배정도 FREE다.
`account_plan.source`(V60)는 누가 배정했는지이며 `OPERATOR`(운영자 배정, 기본값)와 `TRIAL`(출시 전 무료 체험)이다.

## 출시 전 무료 체험

결제를 받기 전이라 플러스·프리미엄 카드의 버튼으로 그 요금제를 14일 동안 무료로 써 보게 한다(리버스 트라이얼). 결제 수단을 받지 않아
체험이 끝나면 자동 결제 없이 무료로 돌아간다.

- **시작:** `POST /api/v1/plan-trials` `{plan: "PLUS" | "PREMIUM"}`. 로그인과 이메일 인증을 마친 회원만 쓴다. 계정 행을 잠근
  짧은 transaction에서 자격을 확인하고, `plan_trial`(V60)에 체험 기록을 남긴 뒤 `account_plan`에 `source = TRIAL`, `assigned_at` = 지금,
  `ends_at` = 지금 + 14일로 배정한다. 응답은 `201`과 새 `GET /api/v1/plan-usage` 본문이다.
- **횟수:** 요금제마다 계정당 한 번이다. `plan_trial`의 기본 키 (계정, 요금제)가 같은 요금제를 두 번 기록하지 않는다.
  프리미엄 체험이 끝난 뒤에도 아직 쓰지 않은 플러스 체험은 남는다.
- **바꾸기:** 지금보다 높은 요금제로만 시작한다. 플러스 체험 중 프리미엄 체험은 바로 바꾸고 새 이용 기간(14일)을 시작하며,
  플러스 체험 때 쓴 양은 넘기지 않는다. 체험 중 [무료로 돌아가기]는 두지 않고 기간이 끝나면 무료로 돌아간다.
  운영자가 배정한 유료 요금제를 쓰는 동안은 체험을 시작하지 않는다(끝난 배정은 무료라 체험할 수 있다).
- **한도:** 체험도 그 요금제의 이용 기간 한도(플러스 500·500·5·10, 프리미엄 1,500·1,500·20·40)를 그대로 쓴다.
- **거절:** 이미 체험한 요금제 `409 PLAN_TRIAL_USED`, 운영자 배정 중이거나 지금보다 높지 않은 요금제 `409 PLAN_TRIAL_UNAVAILABLE`,
  이메일 미인증 `403 PLAN_TRIAL_EMAIL_UNVERIFIED`, 그 밖의 요금제 값 400.
- **조회:** `GET /api/v1/plan-usage`가 `planSource`(`OPERATOR`·`TRIAL`, 무료면 null)와 `trialsAvailable`(지금 시작할 수 있는 체험)을 함께 준다.
- **보류:** 프리미엄 체험을 기업 등록(사업자번호 확인) 회원으로 좁히는 조건은 사용자 결정으로 보류했다. 지금은 이메일 인증 회원 모두가
  두 요금제를 한 번씩 체험한다. 탈퇴 후 재가입으로 체험을 반복하는 남용은 재가입 남용과 함께 다음 단계에서 다룬다.

요금제 종류는 Core `planusage/domain/PlanCode.kt`가 원본이고, DB는 `account_plan.plan_code`의 CHECK 제약으로 같은 세 값만 받는다.
계정 행이 지워지면 배정·사용량 행도 함께 지워진다. 탈퇴는 계정 행을 남기는 soft delete라 사용량 행도 남지만,
다시 가입하면 새 계정으로 0부터 센다(탈퇴 후 재가입 남용은 다음 단계).

## 한도

| 기능 | 로그인 전 | FREE | PLUS(30일 이용권) | PREMIUM(30일 이용권) |
|---|---|---|---|---|
| AI 대화 검색(검색 실행 기준) | 하루 2회 · 결과 2건 | 하루 10회 | 이용 기간 500회 | 이용 기간 1,500회 |
| 공고 원문 질문 | 로그인 필요 | 하루 10회 | 이용 기간 500회 | 이용 기간 1,500회 |
| 신청 문서 초안(공고 하나 = 1건) | 로그인 필요 | 월 3건 | 이용 기간 5건 | 이용 기간 20건 |
| 중복 지원·수혜 검토 | 로그인 필요 | 월 3회 | 이용 기간 10회 | 이용 기간 40회 |
| 도우미 자유 질문 | 로그인 필요 | 이용 가능 | 이용 가능 | 이용 가능 |
| 필터 검색·공고 상세·첨부 받기 | 횟수 제한 없음 | 횟수 제한 없음 | 횟수 제한 없음 | 횟수 제한 없음 |

숫자는 Core `planusage/domain/PlanCode.kt`가 원본이고 모든 요금제에 숫자 한도가 있다. 유료 숫자는 출시 전 출발점이다.
로컬 개발에서는 `PLAN_USAGE_UNLIMITED_ACCOUNT_EMAILS`(Core `app.plan-usage.unlimited-account-emails`)에 적은 계정만 한도 없이 쓴다.
로컬 Compose 기본값은 데모 시드 계정 6개(개발 로그인 `admin@govbiz.local`·`member@govbiz.local`과 `@demo.govbiz.local` 4개)이며,
이 계정도 사용량은 요금제의 기간으로 세고 응답의 `limit`만 null이다. 새로 가입한 계정은 그대로 FREE 한도를 받아 한도 동작을 확인할 수 있다.
운영 Compose는 이 값을 넘기지 않고 `check-production.py`가 값이 있으면 배포를 막는다.
기능별 1회 원가 추정(원문 질문 약 6원, AI 검색 약 4원, 신청 문서 1건 약 30~100원)으로 한도를 매일 다 써도 원가가 순매출(부가세·카드
수수료 제외)의 약 74%를 넘지 않게 잡았고, 실제 사용량을 2~4주 모아 상위 10% 사용자가 거의 닿지 않는 선으로 고친다.
대화 조건 해석은 AI 검색 횟수로 세지 않고 기존 분당 요청 제한만 받는다. 기업 맞춤 리포트의 내부 검색·원문 답변은 리포트 생성 예산으로만 센다.

## 세는 규칙

- **기간:** FREE와 로그인 전은 서울 날짜(AI 검색·원문 질문)와 서울 달력의 달(신청 문서 초안·중복 검토)이다. 유료 요금제는 네 기능 모두
  이용 기간(이용권 시작 시각부터 30일) 총량이며, 키는 그 기간이 시작한 서울 시각(`P20261020T153000`)이다. 기간이 바뀌면 새 기간 키의
  행을 쓰므로 초기화 작업이 없다. 업그레이드(새 배정)는 새 이용 기간을 시작하고 FREE 때 쓴 양은 넘기지 않는다. 이용권이 끝나면
  그때부터 FREE의 하루·달 기준으로 센다. 유료의 짧은 폭주는 기존 분당 요청 제한이 막고, 기간 총량이 원가 상한을 정한다.
- **요청마다 세는 기능(AI 검색·원문 질문):** 분당 요청 제한을 통과한 요청만, AI를 부르기 전에 `plan_usage_counter`(V56) 행을 만들거나
  잠근 뒤 조건부 UPDATE 한 문장(`used_count < limit`)으로 1을 더한다. 동시에 와도 한도를 넘겨 더하지 않는다. 요청이 실패하면 되돌린다.
  검색어가 없는 최신 목록 조회는 AI를 부르지 않아 세지 않는다.
- **작업으로 세는 기능(신청 문서 초안·중복 검토):** 새 작업을 만드는 기존 접수 transaction(계정 행 잠금) 안에서 그 작업까지 센
  이번 기간(FREE는 달, 유료는 이용 기간) 사용량을 확인하고, 넘으면 작업을 남기지 않고 되돌린다. 사용량은 각 기능의 작업 표를 원장으로 읽는다.
  - 중복 검토: 이번 달 시작한 실행 중 대기·실행 중·결과 불명·성공. 실패와 만료로 정리된 실행은 별도 해제 없이 빠진다.
  - 신청 문서 초안: 이번 달 사용자가 시작한 양식 분석·문서 생성·문항별 AI 실행 중 실패하지 않은 것과 만든 문서 파일의 공고 수.
    같은 공고의 분석·생성을 다시 해도 늘지 않는다.
  - 작업 표를 남기지 않는 경로(큐를 쓰지 않는 환경의 이전 동기 양식 분석·문서 생성, 문항별 AI 해석·초안)는 AI를 부르기 전에
    계정 행을 잠근 짧은 transaction에서 그 공고가 이번 달 처음이면 한도를 확인하고 `plan_usage_draft_program`(V58)에 기록한다.
    AI 호출은 transaction 밖에서 하고, 실패하면 그 기록만 지운다. 같은 계정의 작업 접수와 같은 계정 행을 잠가 서로 다른 새 공고를
    동시에 요청해도 한도를 넘지 않는다. 신청 문서를 지워도 기록은 남는다. 이 경로들도 계정별 분당 요청 제한을 지킨다.
  - 신청 문서·중복 검토를 지우면 같은 transaction에서 그 달 사용분을 `plan_usage_counter`에 남겨 삭제로 한도가 늘지 않게 한다(V57).
  - 로컬 목업(`demo_seed_key`)은 세지 않는다.
- **로그인 전 체험:** 접속 주소를 SHA-256으로만 넣은 Redis 키에 다음 서울 자정까지 둔다(Lua로 한도 안일 때만 증가).
  DB에는 남기지 않는다. 같은 회사 망·공용 망에서는 한도를 나눠 쓸 수 있고, 로그인하면 계정 한도를 쓴다.
- **로그인:** 공고 원문 질문과 도우미 자유 질문은 로그인한 회원만 쓴다(없으면 401 `AUTHENTICATION_REQUIRED`).
- **응답:** 한도 초과는 `429 PLAN_QUOTA_EXCEEDED`(`feature`·`period`·`plan`·`limit`·`used`·`resetsAt`·`retryAfterSeconds`,
  `Retry-After`는 이번 기간이 끝날 때까지 초, `period`는 `DAY`·`MONTH`·`PLAN`). 분당 제한 `SUPPORT_PROGRAM_RATE_LIMITED`와 다른 코드다. 사용량 저장소를 읽거나 쓰지 못하면
  유료 기능을 실행하지 않고 `503 QUOTA_UNAVAILABLE`.
- **조회:** `GET /api/v1/plan-usage`가 현재 요금제, 이용권이 끝나는 때(`planEndsAt`, 무료·끝나는 때가 없는 배정은 null)와
  기능별 `feature`·`period`(`DAY`·`MONTH`·`PLAN`)·`limit`·`used`·`resetsAt`(이번 기간이 끝나는 때, +09:00)을 돌려준다(no-store).
  로그인 전에는 `plan: null`과 접속 주소의 AI 대화 검색 체험만 담는다. 작업으로 세는 기능의 `used`에는 진행 중인 작업이 들어가
  한도를 넘을 수 있어 화면은 한도에서 멈춰 보여 준다. 이 값을 보내지 않던 Core 응답도 앱은 끝나는 때 없이 읽고, 모르는 기간의 줄은 뺀다.
- **화면:** 웹은 AI 검색 입력 아래와 원문 질문(상세 패널·질문 화면), 중복 검토 실행 카드, 신청 문서 양식 분석·검토·문서 화면에
  남은 양으로 "오늘 2회 남음"·"이번 달 1건 남음" 줄을 두고, 남은 양이 한도의 20%(최소 1회) 이하면 경고 색과 다시 채워지는 때를
  붙인다(하루 10회는 8회부터, 월 3회는 2회부터, 로그인 전 체험 2회는 1회부터). 다 쓰면 그 기능만 막고 안내를 보인다
  (이미 센 공고의 신청 문서는 다시 만들어도 늘지 않아 막지 않는다). 앱도 신청 문서 양식 분석·초안 만들기와 중복 검토 실행 근처에 같은 줄을 두고,
  거절 응답은 shared 안내 문구로 보여 준다. 웹 프로필과 앱 내 계정은 오늘·이번 달·이번 기간으로 묶어 그 기간이 끝나는 때를 한 번만 적고,
  기능마다 남은 양과 "10회 중 3회 썼어요"를 보여 준다. 끝나는 때는 하루 한도면 "약 3시간 뒤에 다시 채워져요."처럼 화면을 그릴 때의
  남은 시간(시간 단위 반올림, 1시간 미만은 "1시간 안에")으로, 달 한도면 "11월 1일에 다시 채워져요."처럼 날짜로, 이용권 기간이면 "10월 31일 15:30에 이번 기간이 끝나요."처럼 날짜와
  시각으로 적는다. 유료 이용권이면 "10월 31일 15:30까지 이용할 수 있어요."를, 체험이면 "플러스 체험"과 "10월 22일 21:00까지 체험할 수 있어요.
  끝나면 자동 결제 없이 무료로 돌아가요."를 함께 적는다. 웹 프로필은 제목 줄에 [요금제 바꾸기]로 요금제 화면에 잇고, 앱 내 계정은 표시만 한다.
  응답의 `limit`이 null이면(개발용 무제한 계정) 막대 없이 "제한 없음"으로 적고 기능 옆 이용량 줄은 그리지 않는다.
- **요금제 화면:** 웹·앱 모두 카드마다 기능 목록 대신 한도를 적는다(shared `pricingContent`, 한도 위 제목 없음). 무료는 "하루 10회·월 3건"처럼 기간과 함께,
  유료는 가격을 금액을 크게, 이용 기간을 뒤에 작게 "9,900원 / 30일"(부가세 포함)로 적고 한도 줄에는 그 기간의 총량("500회")만 적는다.
  출시 예정가 안내 문장과 "지금 이용 가능"·"출시 예정" 같은 고정 상태 배지는 두지 않는다(사용자 결정). 결제를 아직 받지 않고 가격은 정식 출시 때
  확정한다는 것은 자주 묻는 질문에서 알린다. 무엇을 한 번으로 세는지는 따로 두지 않는다(한도에 닿았을 때 안내 문구에 핵심이 있다).
  로그인해 지금 요금제를 읽으면 그 카드만 굵은 테두리·"이용 중" 배지로 강조하고 추천 강조(플러스)는 뺀다. 웹은 그 카드에 [현재 요금제](비활성)를,
  시작할 수 있는 요금제에 [14일 무료 체험 시작]을 두고 확인 다이얼로그에서 한 번 더 확인한 뒤 시작한다. 앱은 무료 카드의 검색 버튼만 둔다.

## 운영

- 30일 이용권 배정(서울 시각, MySQL 세션은 UTC라 +09:00으로 바꿈):
  `INSERT INTO account_plan (account_id, plan_code, source, assigned_at, ends_at) VALUES (?, 'PLUS', 'OPERATOR', CONVERT_TZ(UTC_TIMESTAMP(6), '+00:00', '+09:00'),
  CONVERT_TZ(UTC_TIMESTAMP(6), '+00:00', '+09:00') + INTERVAL 30 DAY) AS assigned ON DUPLICATE KEY UPDATE plan_code = assigned.plan_code,
  source = assigned.source, assigned_at = assigned.assigned_at, ends_at = assigned.ends_at`. 다시 실행하면 그때부터 새 이용권이 시작되고,
  체험 중인 계정이면 체험 대신 운영자 배정이 된다(체험 기록은 남아 같은 요금제를 다시 체험하지 않는다). 행을 지우면 FREE로 돌아간다.
- 테스트·제휴 계정 상향: 같은 SQL에서 `ends_at`을 NULL로 두면 30일마다 새 이용 기간이 시작되는 배정이다. 검증 스크립트(Compose·카탈로그
  분리·LLMOps)는 검증 DB의 테스트 회원만 PREMIUM(이용 기간 1,500회)으로 올려 호출한다.
- 체험 기록 확인: `SELECT plan_code, started_at, ends_at FROM plan_trial WHERE account_id = ?`. 기록을 지우면 그 요금제를 다시 체험할 수 있다.
- 오늘 사용량 확인: `SELECT feature, period_key, used_count FROM plan_usage_counter WHERE account_id = ? ORDER BY period_key DESC`.
  월 한도의 실제 사용량은 이 값(지운 작업분)과 작업 표 집계를 더한 `GET /api/v1/plan-usage` 값이다.
