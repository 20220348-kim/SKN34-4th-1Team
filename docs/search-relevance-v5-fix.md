# 검색문 오염·관련도 순위·대화 초기화 수정

기준일: 2026-09-07~08. 실제 모델 품질과 코드의 동작 검증을 구분한다.

## 확인한 원인과 수정

1. **검색어에 시스템 정보가 섞였다.** 부산·대전 검색에도 `기준일(서울): 2026-09-07`이 붙어
   서울·날짜·표제 토큰이 키워드 순위와 임베딩에 영향을 주었다. 이제 사용자 질문과 확정한
   지역·업종·지원 목적의 값만 검색한다. 설립일과 서울 기준일은 자격 판단에만 전달한다.
   사용자가 질문에 직접 적은 날짜는 제거하지 않는다.
2. **자격 미확인을 낮은 관련성처럼 취급했다.** 이전에는 대상·지역 점수가 낮으면 총점 60점 컷에
   걸리고, 관련도가 높아도 MATCH 공고 5개 뒤로 밀려 사라질 수 있었다. v5는 관련도와 자격을 분리한다.
3. **이전 대화 조건을 초기화할 실제 버튼이 없었다.** 기존 초기화 로직에 작은 `새 검색` 버튼을 연결하고
   적용 중인 확정 조건을 보여준다. 제안만 받은 조건은 표시·적용하지 않는다. 큰 수동 패널이나 사이드바는 복구하지 않았다.
4. **지원 형태를 좁히는 후속 발화가 기존 활동을 잃을 수 있었다.** `사업화 지원 → 지원금 위주`는
   `사업화 지원금`으로 정교화하고, 명시적인 `사업화 말고 수출`이나 전체 초기화와 구분하도록 프롬프트 예시를 보강했다.
   단어별 분기 규칙을 production 코드에 추가하지 않았다.

## v5 정책과 실행 흐름

`totalScore = 2 × (semanticRelevance 0~40 + supportTypeFit 0~10)`이다.
이 관련도는 신청 가능성이나 선정 확률이 아니다. 대상·지역 점수와 접수 상태 가산점은 제거했다.

- `semanticRelevance >= 20`: 요청의 필수 활동·지원 형태를 직접 제공해야 한다. 일부 지원을 인정한다는 이유로
  지원금 요청을 단순 컨설팅으로 바꾸거나 필수 요청을 생략하지 않는다. 지원 형태를 정하지 않은 넓은 질문은 구분한다.
- 대상·지역 중 하나라도 본문 근거상 `INCOMPATIBLE`이면 제외한다.
- `UNKNOWN`은 확인 필요로 표시한다. 관련도 감점이나 후순위 강제 사유로 삼지 않는다.
- 관련도 내림차순, 동점이면 원래 후보 순서로 최대 5개를 반환한다. Core도 동점 순서를 검증한다.
- 원문 정확 인용·설명·길이·후보 ID·절단된 원문의 UNKNOWN 검증은 유지한다.
- 화면은 서버 순서를 그대로 표시하고 카드별 자격 배지·인용을 유지한다.

`HTTP API → Service → Agent → OpenAI → Response`의 기존 AI 호출 구조를 유지한다.
Core 검색은 `MySQL 조회 → 접수 상태 필터 → 깨끗한 검색문 → 의미·키워드 후보 결합 → AI 랭킹 → 계약 검증`이다.
외부 의존성·검색 한 번의 호출 횟수·DB 스키마는 바꾸지 않았다. LangChain/LangGraph를 추가하지 않았다.
후속 실측에 따라 랭킹 전용 모델·추론 설정을 분리했다. 정확도 우선 프로필은 Sol/low이며
대화·RAG는 기존 공통 모델을 유지한다. 전용 설정이 없으면 기존 모델/none을 상속하므로
기존 `.env` 사용자는 두 전용 환경변수를 명시해야 같은 품질 설정을 사용한다.

## 회귀 검증

- 수정 전 검색문 회귀 4건과 고관련도 UNKNOWN 순서 회귀 1건의 실패를 확인했다.
- Core: JDK 21 `./gradlew clean test --no-daemon`, **519건, 실패·오류·건너뜀 0**.
  실제 MySQL 8.4 Testcontainers를 포함한다.
- AI Service: 최종 전체 **616건 통과**. UNKNOWN 조합별 점수 불변, 낮은 MATCH 5개에 의한 누락,
  동점 순서, 의미 최소 기준, 잘못된 구식 점수 필드, 인용 검증을 포함한다.
  실행은 잠금 의존성이 설치된 `.venv/bin/python -B -m pytest -o addopts='' -q -p no:cacheprovider`였다.
  별도로 `uv lock --check`, `uv pip check`, sdist/wheel 빌드를 통과했다.
- Frontend: **29파일 299건 통과**, TypeScript·Vite build·Oxlint 통과.
  실제 버튼 클릭에 의한 초기화·요청 취소·늦은 응답 무시·입력 포커스·서버 순서 보존을 검증한다.
- 실제 headless Chrome: 1280×900 / 360×800, `/` / `/chat` 4조합에서 초기화 버튼 접근,
  미확정 조건 비적용, 확정 후 조건 표시, 카드 순서와 스크린리더 집계 일치를 확인했다.
  가상 응답 검증이며 실제 모델 품질 테스트가 아니다.
- 검색 평가 도구 최종 **108건**, 라벨·공유 검토 도구 **108건**, 근거 답변 평가 도구 **122건** 통과.
  v4 지역 평가 기록의 원래 요청 해시를 보존하며 v5 기록에 버전을 명시한다.
- 최종 격리 Compose: 더미 키·대역과 외부 통신 차단 네트워크에서 Web 프록시를 통한 실제
  MySQL/Qdrant·Core/AI HTTP 검색, 기업 조건 검색·의도 정교화·학습 예제를 확인했다.
  합성 공고 27건의 준비 상태는 `SEARCHABLE`이었다. 랭킹 4건은 Sol/low,
  조건 해석 1건은 Luna/none으로 실제 SDK 요청 설정까지 일치했다.
  기업마당 중단 후 DB 조회 유지, Qdrant 중단 시 검색 503·`UNAVAILABLE`와 목록 유지,
  AI 중단 시 명시적 오류와 Core 재시작 없는 복구를 확인했다. 유료 호출은 0회다.
  최종 실행의 전용 컨테이너 7개·더미 볼륨 3개·네트워크 1개는 모두 정리했고,
  실행 전후 기존 사용자 자원은 동일했다. 통합 동작 검증이지 실제 추천 품질 점수가 아니다.

실제 대표 질문 3개와 서울 사례 재검증은
[첫 실행 기록](../evaluation/support-program-search/runs/search-relevance-v5-20260907-v1/README.md)에 있다.
서울 SW 질문에서 영화 제작 공고 2개가 사라졌지만, 남은 공고의 지원금 제공 방식이 불명확했다.
후속 [고정 후보 비교](../evaluation/support-program-search/runs/search-precision-v5-20260907-v1/README.md)는
같은 공고 20개로 Luna/none 13회, Luna/low 6회, Sol/low 6회를 실행했다. 지원금 질문뿐 아니라
컨설팅·영화 질문의 양성 보존과 반복 편차를 함께 확인했고, 실패한 설정도 모두 기록했다.
Sol/low에서 지원금 질문·표현 변형·반복은 모두의 창업만 반환하고, 컨설팅은 관련 공고 3개,
영화 후반작업은 해당 공고 1개를 반환했다. 랭킹 실행 시간은 약 31~43초로 늘었다.
최종 로컬 서비스의 서울 SW 지원금 검색도 HTTP 200 / 50.741초 / 모두의 창업 1개로 확인했다.
DB 1,506건과 색인 준비 상태를 유지했고, 표시된 100점은 정확도나 신청 가능 확률 100%가 아니다.
사전 검토는 AI 초안이며 사람 정답이 아니다. 단일 도메인의 소수 결과를 전체 품질 개선 수치로 주장하지 않는다.

## Docker 실행 코드 일치

추가 실험의 시작 검사에서 `/app/app`은 v5인데 설치된 wheel은 v1인 문제를 발견했다.
임시 경로에서 실행하면 구버전을 가져올 수 있어 API 호출 전에 두 차례 중단했고, 잘못된 결과는 생성하지 않았다.
진단 실행은 `PYTHONPATH=/app`과 v5 검사로 실제 서버 소스를 고정했다.
Docker 마지막 설치에 애플리케이션 패키지 재설치를 명시해 소스 변경 시 오래된 wheel 캐시를 재사용하지 않도록 했다.
수정 후 warm-cache 빌드와 `python -I -B`에서 로컬·이미지·설치본의 Python 35개 해시 일치 및 v5 import를 확인했다.
다른 의존성 캐시는 유지한다. [uv 캐시 기준](https://docs.astral.sh/uv/concepts/cache/#dynamic-metadata)과
[패키지 재설치 옵션](https://docs.astral.sh/uv/reference/cli/#uv-sync--reinstall-package)을 참고했다.

## 고정 공고에서 확인한 검색문 오염

공유된 1,422건 `fixture-unlabeled.json`에 현재 키워드 토큰화·정렬 규칙을 적용해
시스템 표제·기준일이 붙은 검색문과 수정 검색문을 비교했다. 의미 검색과 실제 LLM 호출은 하지 않았다.

| 질문·조건 | 변경 전후 키워드 상위 20개 중 동일 공고 수 |
|---|---:|
| 수출 지원 / 부산 / 제조업 | 6 |
| 창업 지원 / 제주 / 관광 | 9 |
| AI 기술개발 / 대전 / 인공지능 | 7 |

대전 AI 질문에서 `BIZINFO:PBLN_000000000126030` 서울 가치소비 기획전은 키워드 3위였지만
수정 후 상위 20개 밖으로 빠졌다. 기존 일치 토큰은 `서울·2026·09·07·기업`으로 실제 질문 주제와 무관했다.
상위 결과가 바뀌었다는 사실이나 이 사례 하나를 Recall/MRR 개선 수치로 해석하지 않는다.

## 남는 한계와 다음 판단

- 후보는 기존 RRF 결합 최대 20개다. 한국어 조사·동의어가 완전 일치 키워드에 불리한 문제나 후보 누락을
  모두 해결한 것은 아니다. 실제 후보 단계 평가 후에 검색 방식·후보 수를 비교해야 한다.
- `searchWithTrace`는 기업 조건을 받을 수 있지만 기존 `evaluation-capture` CLI 파일은 여전히 단문 질의 형식이다.
  기존 평가를 대화 해석·기업 조건까지 포함한 평가로 해석하지 않는다.
- 프롬프트 예시와 고정 모델 응답 테스트는 실제 모델의 의도 보존을 보장하지 않는다.
- v3/v4 과거 캡처와 점수를 덮어쓰거나 v5 성능처럼 재사용하지 않는다. 학습·예제 코드는 보존했다.
- 실제 확인은 승인된 대표 질문으로 수행하고, 결과·실패·범위를 별도 실행 기록에 남긴다.

프롬프트의 정책·예시와 단계별 검증은 OpenAI Docs 스킬을 사용해
[공식 프롬프트 안내](https://developers.openai.com/api/docs/guides/prompt-engineering)와
[평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 참고했다.
